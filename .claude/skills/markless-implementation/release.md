# Release Workflow

- Publishing happens from CI, not from a laptop. `.github/workflows/release.yml` publishes to npm via trusted publishing: GitHub mints a short-lived OIDC token, the npm CLI trades it with the registry, and no npm token is stored anywhere in this repository. The workflow asserts a stored token is absent rather than trusting that nobody added one.
- Publish authority is therefore "whoever can land a change to `.github/workflows/release.yml` and dispatch it", not "whoever holds the owner's npm 2FA device". Treat any edit to that workflow, or to the `scripts/release/` code it runs, as a change to who can publish.
- The workflow filename is load-bearing. Every package's trusted-publisher entry on npmjs.com names `release.yml` literally, so renaming the file silently breaks publishing for all of them, with an authentication error that says nothing about a rename.
- Markless releases minor versions only (0.6.0, 0.7.0, ...); there are no patch or major releases and no release-type input anywhere. A release is one dispatch: `gh workflow run release.yml --ref main -f mode=cut`. Its `cut` job releases the newest `main` commit whose push CI run passed every check `main` requires (refusing when no commit since the last release is green, or when the newest nightly `screen-reader.yml` run on main it contains is red or over 72 hours old: `scripts/release/reader-gate.mjs`), runs `scripts/release/cut.mjs` on it (bumpp to the next minor, `sync-version.mjs`, the `release:notes --changelog` section in `CHANGELOG.md`, a hooked commit as `github-actions[bot]`), lands it through `main`'s squashing merge queue with `scripts/release/land.mjs`, and tags `vX.Y.0` on the commit the queue landed, never before `main` contains it; the `release` job publishes that tag; the `announce` job creates the GitHub Release from the changelog section, after a cut or a manual `publish` recovery alike. The cut lives in `release.yml` because npm checks the dispatched workflow's filename, so a separate workflow calling this one could not publish. `mode=cut-dry-run` or `pnpm release:cut --dry-run` rehearses everything except tag, push, publish and Release. How-to and one-time setup: `docs/ci-process.md`, "Cutting a release".
- Nothing publishes on a merge or a tag push. The only trigger is `workflow_dispatch` and it defaults to dry-run. Manual `publish` mode requires a typed confirmation phrase matching the version; every publish, cut or manual, runs only on the commit tagged `v<version>`. A green dry run proves packaging and version lockstep; it does not prove the OIDC exchange or provenance, so only a real publish proves those.
- The `release` job never bumps versions or writes to git: the version must already equal the root version and every release package version at the tag. Only the `cut` job commits and tags, only `announce` creates GitHub Releases, neither holds `id-token: write`, and no job reads a secret. When `scripts/release/inherit-ci.mjs` proves by diffing the trees that the release commit changed only top-level `package.json` versions and `CHANGELOG.md` on the green commit, it posts each required check as a commit status linking that green run. Otherwise the full `ci.yml` runs on it as a pull request from a temporary `release/vX.Y.0` branch (main's ruleset ignores required checks from a `workflow_dispatch` run) and `scripts/release/required-checks.mjs` confirms each required check passed in that `pull_request` run.
- `main` takes changes only through its merge queue, which squashes, so the release commit never reaches `main` and the cut never pushes to it. A queue entry the workflow token enqueues gets no CI run (GitHub starts no workflow for its own token's events; 0.10.0 sat 4 hours and was dropped), so `land.mjs` posts the inherited statuses on the queue's commit, and only after proving it is its parent plus versions and `CHANGELOG.md`, in version lockstep, with a parent green in `ci.yml`. Those two scripts are the only places a release posts a commit status. The tag message records `Cut from <sha>`, where the next changelog section starts. A release can be on `main` without its tag being an ancestor (0.10.0); the cut then takes the release point as the commit where `main` took that version. Never move a published tag.
- Attaching a trusted publisher to a package is owner-side on npmjs.com and cannot be automated from this repo. npm cannot attach one to a name that has never been published, so a first-time package needs a one-time owner-run bootstrap publish before CI can take over.
- The release set is derived from the workspace by `scripts/release/release-packages.mjs`, never restated as a literal list. Three copies of that list existed and each drifted, which is how the `--all` guard sweep silently stopped checking two packages.
- Establish package and dependency closure before packing: intended packages, versions, workspace dependency ranges, build order, included files, and public entry points must agree.
- Run `vp pack`, inspect the produced tarballs, and install them in a clean consumer to verify imports, types, runtime behavior, and the absence of workspace-only dependencies or unintended files.
- Release scripts must be fail-closed and resumable. Validate prerequisites before mutation, record completed stages, stop on ambiguous state, and make reruns skip only steps already verified.
- After publication, verify registry versions and dist-tags, package contents, provenance attestations for every published package, repository tags, and GitHub release metadata against the release plan.
- Package or tooling changes must also read `implementation.md` and `bundler.md`.
