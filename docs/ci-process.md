# Keeping CI green

How to stop pushing red to `main` without weakening any check. The evidence behind each rule is in [ci-failure-history.md](./ci-failure-history.md): over twelve weeks `main` was red 85% of the time, and 59% of pushes to `main` landed on a `main` that was already red.

Three causes account for almost all of it:

1. **The CI command was never run before the push.** Most red runs are ordinary test, typecheck, box, or byte-budget failures that fail the same way on a Mac. 99 of 122 pushes to `main` skipped a PR, so CI saw them first.
2. **Red was left red.** Once `main` is red, the next push cannot tell whether it broke something, so breaks pile up (the 32-day and 25-day stretches each hold several separate regressions).
3. **A local run is not a CI run.** `pnpm test` runs a different command set from `ci.yml`; the Mac has browsers, tools, and untracked files the runner does not; some failures only happen on Linux.

The process below answers each one.

## 1. `pnpm ci:local`: run exactly what CI runs

For a write task only `--affected` runs locally; the full unit suite and heavier jobs run on the pull request (section 3).

`scripts/ci/local.mjs` reads `.github/workflows/ci.yml` at run time and runs each job's `run:` steps. Nothing is copied from the YAML by hand, so a step added to the workflow is picked up automatically. The only thing the script owns is a small table saying, for each job with checks, whether it belongs to the fast set, the full set, or runs only in CI. A new job without an entry makes the script exit with an error that names it, so the table cannot fall behind silently.

```sh
pnpm ci:local --list      # every job and step in ci.yml, and what runs locally
pnpm ci:local --affected  # fast jobs, unit tests narrowed to what the diff from origin/main can reach
pnpm ci:local             # fast mode (same as --fast): every unit test (debugging a CI failure)
pnpm ci:local --full      # every job this machine can run (debugging only: the PR's CI run is the receipt)
pnpm ci:local --job browser --job boxes-router   # just these jobs
pnpm ci:local --clean     # same, in a throwaway worktree of HEAD
pnpm ci:local --linux     # each job in its own Linux container (needs docker)
pnpm ci:local --install   # also run the jobs' setup steps (pnpm install, Playwright)
pnpm ci:local --workflow .github/workflows/screen-reader.yml --list
```

How steps are sorted:

- **check**: a `run:` step that tests something. These run.
- **setup**: `pnpm install`, `corepack enable`, `playwright install`. Run only with `--install`.
- **skipped**: `uses:` actions, lane cache markers, and steps whose `if:` or command reads GitHub context (`needs.`, `steps.`, `github.`). These are CI plumbing: locally every lane runs, so there is no cache hit to test for.

Sharded jobs (`--shard=${{ matrix.shard }}`) run once, unsharded. Other matrices (the screen-reader families) expand, and a command repeated across matrix entries runs once. Every command runs with `CI=true`, the job's `env:`, and `bash -eo pipefail`, as on the runner.

### Perf guards

`pnpm perf:guard` used to run only at the end of `pnpm test`, which CI does not run, so its failures were invisible. From 2026-10-06 to 2026-10-21 the guard measured the docs site's 404 page three times: the docs moved to the site root, while `SITES` in `scripts/benchmarks/perf-guards/config.mjs` still listed `/markless/*`. The guard now reads the base from `website/site-base.ts` and stops when a guarded route does not answer 200. The `perf-guards` lane runs the full set on every PR whose inputs changed: 5 min 51 s on the runner, 5 min 16 s of it the guards, shorter than the slowest `unit` shard at 7 min 18 s, so a per-PR subset would not shorten a PR's wait.

On the real docs pages G2 (no JS fetched by a control's first use) first failed 17 times on this Mac and 22 on the runner. The 17 were the `<Code>` playground, whose boot loads its session, editor, compile worker and result frame. A block now downloads all of it when it scrolls into view or the page goes idle (`components/docs/code/prefetch.ts`, listed per block in `_code-prefetch.json` by `tooling/code-prefetch.ts`). It downloads without running anything: `modulepreload` for the page's modules, `prefetch` into the HTTP cache for the worker and frame. The other five were the router's idle link preload landing after the guard's first click on the slower runner. The guard now waits until an idle period passes with no new request before the first input, and counts a request only when it reaches the network: a file the HTTP cache answers transfers nothing and costs no round trip.

## 2. Linux parity

Some failures only happen on the Ubuntu runner: the HMR reload race (null-byte module re-read), the `yuku-tsrx` Linux binding, Chromium's Shift+F10 handling in `context-gate`, and every "job forgot to install a browser" failure.

**Feasibility on this Mac, measured:** `docker`, `act`, `colima`, `podman` and OrbStack are not installed (`command -v` finds none, no app in `/Applications`, nothing in `brew list`). So Linux parity cannot run here today. `pnpm ci:local --linux` exits with code 2 and says so. The code path is written but has not been run.

What `--linux` does once a container runtime exists:

1. `git archive HEAD` streams the committed tree (not the working copy) into a `node:24-bookworm` container (`--platform linux/amd64`, the runner's architecture).
2. One container per job. Inside: `git init` so `agent-files` can diff, pnpm 10.33.2 via corepack, `pnpm install --frozen-lockfile`, then `local.mjs --install --job <id>`, which runs **only that job's own setup steps** before its checks. As root on Linux, `playwright install-deps` runs too.

To enable it (owner decision, it installs software): `brew install colima docker && colima start --cpu 6 --memory 12 --arch x86_64`. x86 emulation on Apple Silicon is slow; `--arch aarch64` is faster but no longer matches the runner's CPU, which matters for native bindings like `yuku-tsrx`.

Why not `act`: it replays the whole workflow including `actions/cache`, artifacts, and the lane gate, needs a 12 to 20 GB runner image to match `ubuntu-latest`, and still emulates x86 on this Mac. `--linux` runs the same commands with only the container part added. `act` stays useful for debugging the workflow file itself (a new `if:`, a new artifact path); `act -n` (dry run) is cheap for that.

When to use it: before pushing anything that touches the HMR/dev server, native dependencies, keyboard or focus handling in browser tests, or the workflow's install steps. Otherwise, a PR run is the Linux check.

## 3. What runs where (agents and PM)

Heavy verification runs on GitHub Actions, not on this Mac. The org's plan runs 60 jobs at once; this Mac runs about three heavy commands before everything on it slows down, and the load itself made tests flaky.

1. **Locally, every write task:** `pnpm run typecheck` and `pnpm ci:local --affected`. That runs the fast jobs (agent files, lint, both typechecks) in full and the unit tests the yuku module graph selects for the diff from the merge base with `origin/main`, counting commits, staged and unstaged edits and untracked files. Selected tests that `scripts/ci/heavy-tests.json` declares (they build an app or launch a browser) are left to the PR's `unit` job, which runs every test; `--with-heavy` runs them locally too. Those 143 of 1,028 test files took 1,310 of the node project's 1,814 CPU-seconds on this Mac (72%, measured 2026-11-18), and a runtime or compiler change reaches nearly all of them. A config, lockfile, workspace-manifest or unclassified change still selects every unit test, heavy ones included. The pre-commit hook runs the same selection for the staged change on every commit. A passing `ci:local` run of the whole fast set records the tree it checked under `.git/markless-ci-pass/<tree hash>.json` (`scripts/ci/pass-record.mjs`). The hook skips the fast jobs when the commit's tree is that tree, nothing on disk differs from it, and the recorded run covered every test the commit selects, so a commit straight after a passing `--affected` run does not run the same jobs twice. The hook's own lint and agent-file drift check still run. The whole unit suite runs in the PR's `unit` job; run `pnpm ci:local --fast` locally only to debug a failure there. Three whole-suite runs at once held an 18-core Mac at a load of 36 to 54 (2026-11-18), which is why the local run is narrowed. `VITEST_MAX_WORKERS=<n>` caps the workers of any local unit run; vitest reads it over the config's `maxWorkers`.
2. **On GitHub, through the pull request:** everything heavier. That means the unit and browser shards, perf-guards, the website boxes and the migrate checks. Push the branch, open the PR, and let CI run. The lanes that never caught anything alone on a pull request (the `boxes-*` lanes, the receipt set, demo boxes, build-scale, build-warnings, completion-matrix, typecheck-ts7, the package-manager matrix and the benchmark) run in the merge queue and on `main` only; see "Lanes" below.
3. **Do not watch your own CI.** Push, then do the next piece of work or send the report, and check the run once when it should be done (a PR CI run takes a median of 13.8 minutes, measured 2026-11-18). Sitting on `gh pr checks --watch` or `gh run watch` cost about 16 worker-hours in one night.
4. **The receipt is the PR's green CI run** on the exact commit: its run URL, or the commit's check summary. No task is reported done before that run is green. The merge-queue-only lanes are not in it; the queue runs them before the change reaches `main`, and a change that fails one leaves the queue like any other red lane. "Green on N local runs" in prose is not a receipt.
5. **Local heavy runs are for debugging one specific failure:** `pnpm ci:local --job <id>`, or the single test file. They do not replace the PR run.
6. **A/B build timings** go through the `Build timing` workflow (`gh workflow run build-timing.yml -f base=<ref> -f head=<ref> -f app=<dir> -f rounds=<n>`), which interleaves both refs on one runner. No scratch branches.

Multi-commit series (for example a migration done unit by unit) go on a branch with a PR. `main` gets the series after the PR is green, not one red commit at a time. The vite-plus migration put 21 consecutive red commits on `main` this way.

A release commit runs `pnpm release:check` and `--fast`; a new package additionally needs its npm trusted-publisher entry before the first publish (two release runs failed with `E404` on a package's first publish).

### Lanes: what each proves and when it runs

Every job in `ci.yml` runs in the merge queue and on pushes to `main`; all but the merge-queue-only lanes also run on pull requests. A content-hashed lane skips its work when its inputs already went green: each lane decides that itself in its first step (`.github/actions/lane-hash`), and on a hit it finishes green in seconds. A push the merge queue already tested does the same in every lane. The required checks are `test`, `typecheck` and `agent-files`.

**Merge-queue-only lanes.** A lane with the job-level `if: github.event_name != 'pull_request'` skips on pull requests. `test` reads that `skipped` as passing on a pull request only: its `gate` step lists every such lane in `QUEUE_ONLY_RESULTS` and fails a merge-queue, `main` or dispatched run where any of them did not succeed. `check-workflow.mjs` (rule 5b) fails the workflow if a lane skips pull requests in any other form, if the list and the lanes disagree, if a required check or a job the gate reads `skipped` past skips pull requests, or if the box lanes skip pull requests while `test` still builds the receipt set on them. Which lanes qualify was measured: over 580 pull-request head commits from 2026-11-18 03:00Z to 2026-11-21 03:00Z (193 pushes a day, 34 jobs each), none of these lanes failed on a commit where every other job passed, and the receipt steps inside `test` never failed on a pull request. Together they took 3,514 runner-minutes a day on pull requests and about 2,570 of the 5,724 jobs a day pull requests started. A lane that later catches something on its own goes back on pull requests. `screen-reader.yml`'s `virtual` lane caught nothing alone either, but it stays on pull requests: it never runs in the merge queue, so moving it would leave it no run before `main`. The lanes that do catch defects alone stay on every pull request: perf-guards (36 commits), unit-budget (34), unit (30), browser (5), website-boxes (3).

## 4. Flake policy

A flake is a test that fails and passes on the same code. Rules:

- **No silent retries.** Do not add `retry:` to vitest projects, `--retries` to Playwright, or rerun loops in the workflow. A rerun of a red CI run is allowed once, by a person, with a note in the PR or ledger saying which test and why it is believed to be noise.
- **Quarantine is explicit and expires.** A flaky test may be moved to a quarantine list (for example `test.skip` behind a `QUARANTINED` marker naming the owner and an expiry date, at most two weeks out) in the same commit that files the fix task. An expired entry fails CI, so quarantine cannot become permanent. The quarantine list is small and visible, never a pattern in a config.
- **Fix the mechanism, not the timeout.** Raising a timeout is acceptable only with a measured reason (the test's real work takes longer on the runner). The recurring flakes all have concrete mechanisms:
    - `expect.poll` windows too short under load (`capture-slot-binding`, `broadcast-diamond`): wait on the event the test is about (a settle promise, a DOM mutation) instead of a fixed poll window.
    - 5-second timeouts on a cold TypeScript language service (`language.test.ts`, `create.test.ts`): warm the service once in `beforeAll`, or give the known-slow test its own measured timeout.
    - `server.watcher.unwatch(root)` right after `createServer` (`ssr-browser-hmr`): chokidar ignores the root's children only once its asynchronous first scan has registered the root, so on linux the test's own file writes still arrive as watcher events. A test that emits its own watcher events creates the server with `server.watch: null`.
    - Server `close timed out after 10000ms` in boxes: close idle keep-alive connections before `close()`.
    - A test that times out keeps running while `afterEach` runs (`ssr-browser-hmr`: "Failed to load url ... Does the file exist?" in the next test). `afterEach` closes every server a test started before it removes the test's temp root.
    - A child process's log line or a Playwright `response` handler's body read can arrive after the response the test awaited (`stream-settle-failure`, `lookup-table-imports`). Await the line (`BuiltServer.waitForOutput`) or the handler's own promise; do not read the value synchronously.
    - A unit job's first WebKit page pays the runner's cold start: whichever file opens WebKit first in a shard (`navigation-stream`, `page-region`, `top-level-control-flow`) spent 3 to 13 s on its first test in passing queue runs on 2026-11-20 and over 30 s in two failing ones, while the first test of every later WebKit file in the same job took under 1 s, in a newly launched browser too. The unit job shows one WebKit page before the tests (`scripts/ci/warm-webkit.mjs`), as the box jobs do for Chrome (`warm-chrome.mjs`).
    - A whole Vite build, dev server start or child `npm` process under the 5 s default (`rolldown`, `ssr-browser-hmr`, `create`): measured at 2 to 7 s at load average 80 to 110 on the 18-core Mac, so these tests carry a stated 30 s timeout. The same holds for tests that spawn `markless-tsc`, TypeScript 7.1 or tsserver, or compile or type-check a large input (`markless-tsc`, `language`, `template-dynamic-import`, `doctrine-guard`, `node-in-browser-fixture`, `static-arm-literal-text`, `storage-types`): 2.3 to 4.2 s alone at load average 54, so they carry 30 s. `router/test/package-build` packs and type-checks the router in 22.8 s alone at that load and carries 120 s. `scripts/release/publish-workspace` runs the publisher as a child Node process that starts about thirty fake `pnpm` and `npm` tools per test: 0.5 to 1.2 s alone and up to 2.1 s with six copies at load average 24, past 5 s in the pre-commit run at 35, so it carries 30 s; its registry deadline is out of reach of those runs, so only the scripted answers end the wait.
    - Fixed ports: bundler tests on 4218 and 4346 to 4348, router boxes on 3000, music-player boxes on 4173, perf guards on 4221 to 4224. Listen on port `0` and read the assigned port back, as the other tests already do. Where a fixed port is unavoidable, make it overridable (as `MARKLESS_PERF_GUARD_PORTS` does) and fail fast with "port in use" rather than timing out.
- **Timing benchmarks are not correctness checks.** `benchmark-guard` timing rows are known to be two-speed on runners (`07_create10k`). A timing-only red on a diff that cannot reach the benchmark bundles gets one rerun, recorded; size rows are deterministic and are never rerun away. Each benchmark shard now builds the benchmark app from the baseline checkout and from the current one before timing anything (`scripts/benchmarks/jsfb-bundle-digest.mjs`). When every file in both `dist` folders is byte-identical, after the checkout's own path is written out of them, nothing a benchmark loads changed: the shard skips the timing and the guard passes. If the shards disagree, the build is not deterministic and the guard fails. From 2026-10-21 21:49 to 2026-10-22 07:53, 8 of 69 guard runs went red, and in every one the two builds emitted the same content-hashed chunks (read from the shard logs), so those 8 were noise (11.6% of runs). The one run in that window whose builds differed was timed and passed. With the identity check, all 8 would have passed without timing. Timing still runs, with the same noise, whenever the built app differs.

### Stale merge-queue runs

When the merge queue rebuilds its groups (an entry fails, times out or leaves), GitHub deletes the old `gh-readonly-queue/*` branches but leaves their runs queued for runners. `stale-queue-runs.yml` cancels any `merge_group` run whose branch no longer exists, listing each one in its run summary. It runs whenever a merge-queue CI run is requested, which is what a rebuild does, and on a 10-minute schedule as a backstop: under load GitHub dropped that schedule to 4 runs in 30 hours (2026-11-18 to 19). On 2026-10-28 five such runs, about 32 jobs each, were waiting behind the live groups.

## 5. Keeping `main` green

- **A red `main` blocks every push except the fix.** When `main` goes red, the next push to `main` must be the fix or a revert of the breaking commit. Everything else waits on a branch. This is the rule that would have prevented the 70 pushes onto an already-red `main`.
- **Revert first when the fix is not quick.** If the cause is not fixed within a working session (a few hours), revert the breaking commit and fix forward on a branch, as was done for the HMR barrier change (`a26de5e5` reverted by `dc6e20f1`).
- **Whoever pushed the break owns the fix.** For agent work, the PM assigns the fix task before dispatching anything else that pushes.
- **A pre-existing red is a task, not background.** If a check is red on `main` when a goal starts, the first task is to fix it or quarantine it under the flake policy. Do not work around it and do not describe new failures as "the same red".
- **Branch protection (owner action).** `main` has no branch protection today. Requiring the `test` gate, `typecheck`, and `agent-files` status checks would turn this rule from a habit into a mechanism. `package-manager-matrix` and `benchmark-guard` are already designed to block as separate checks once required.

## 6. Budgets and anchors

Byte walls and budgets failed 54 runs, usually by a few bytes to a few hundred. The existing performance-guard model is the rule for all of them:

- Changing a budget or anchor requires a one-line reason in the same commit (`pnpm perf:guard:accept <guard> "<subject>" --reason "<one line>"` for the perf guards, `MARKLESS_ACCEPT_FIXTURE_RUNTIME=1 MARKLESS_ACCEPT_REASON="<one line>"` for the `fixture-builds` anchors and walls, and `node scripts/benchmarks/build-scale/guard.mjs accept --reason "<one line>"` for the build-scale client module and compile counts, all recorded as a change file (below); the same shape for the music-player budgets, box byte walls, and the `reason` beside each other budget in `scripts/benchmarks/build-scale/budgets.json`).
- Re-anchoring is a decision, not a fix: the reason says what the extra bytes buy, or which win the lower anchor records.
- A big win re-anchors in the same change set, so the anchor stays close to reality.
- Byte walls must be measured the way CI measures them (a clean tree, through the same test). `ci:local --clean` does that; a hand-run demo build does not.
- The `fixture-builds` child builds run with `NODE_ENV=production`, although vitest sets `NODE_ENV=test`. Under `test`, `import.meta.env.DEV` is true, so development-only checks (and the modules only they import) are built and counted in the per-module figures though they never ship; under `production` they fold away, so the lane counts only shipped code.

The `fixture-builds` walls have been seen to differ between worktrees on the same Mac. Until that is explained, a wall that passes in one checkout and fails in another is treated as an environment bug to fix, not as slack to spend.

### Pull requests that move the same anchors at the same time

**The problem.** The perf-guard anchors (`scripts/benchmarks/perf-guards/anchors.json`), the fixture runtime anchors and the `fixture-builds` gzip walls were absolute numbers on shared lines. Every pull request that moved output size rewrote the same lines and appended to the end of the same `history` array. When one merged, every other open one conflicted on those lines, and its numbers were wrong by the first one's cost, so it had to be measured again on CI. #430 went through about ten rounds of this while #428, #433, #435, #440, #441, #442 and #443 merged ahead of it; 81 of the 368 commits on `main` from 2026-10-01 to 2026-11-03 touched `anchors.json`, 55 the fixture runtime anchors and 28 `fixture-builds.test.ts`. The history shows the workaround done by hand: "then carried onto the anchors of #433" means adding the other pull request's cost to one's own numbers.

**Options considered.**

- **Each pull request records its own change in its own file, and a guard's limit is `main`'s anchor plus the recorded changes (chosen).** No two pull requests write the same line, so they cannot conflict. The changes add up: after #441 lands with `+18 B`, the tree of a second pull request built on top of it is checked against `anchor + 18 + its own change`, which is what that tree should measure. Nothing is loosened: the budget around each limit is the same, and the only thing that moves a limit is a recorded change with a reason.
- **The merge queue measures again and checks against an allowance each pull request declares.** Rejected. The queue builds a squash of the pull request and cannot write the new measurement back to `main` (only a bot pushing to `main` past the ruleset could), so `main`'s anchors would go stale, against the stale-measurements rule. An allowance is a ceiling a pull request does not have to use up, so it is looser than a measurement.
- **Anchors are generated from `main`'s own measurement after each merge, with a reason entry per pull request.** Rejected. A job would have to commit to `main` after every merge (past the merge queue) or open a pull request per merge that conflicts in turn, and `main` would be wrong between the merge and the regeneration. Taking whatever `main` measures as the next anchor would also turn any growth that slipped in into the new anchor without a reason.

**How it works.**

- The anchor files stay where they are and hold `main`'s anchors as of the last fold (below). Each pull request that moves an anchor adds one file, `scripts/benchmarks/anchor-changes/<branch>.json`. Every entry in it names one anchor (`surface`, the anchor file it belongs to, and `path`, the keys inside it), the change, a one-line `reason`, and the date. A number changes by `delta` (`+18`, `-240`); a new anchor (a new runtime module) is `set`; a vanished one is `remove`; an allow-list entry is `append`.
- A guard reads its anchors as the anchor file with every change file applied (`scripts/benchmarks/anchor-ledger.mjs`), then checks exactly as before: the G16 load budget is `+256` executed chars and `+48 B` downloaded (the composition allowance below), G10 is still `+128 B` rendered per module, a `fixture-builds` wall is still its measured value plus the same margin. Executed and downloaded numbers stay separate fields (`executedChars`, `jsGzipBytes`), and the walls are labelled as emitted gzip bytes.
- The accept commands write the current branch's change file instead of editing the anchor file. The change they record is this tree's measurement minus its merge-base's (`git merge-base HEAD origin/main`), both taken on the same machine with the same command: `fixture-builds` builds each fixture in a throwaway checkout of the merge-base too, and `perf:guard:accept` measures one unless `--base <measurement.json>` hands it one. Running accept again after a rebase replaces this branch's entries instead of adding to them. Accept still needs `--reason` (or `MARKLESS_ACCEPT_REASON` for `fixture-builds`), and a win is still recorded in the same change set, as a negative `delta`.
- Why the merge-base and not the anchors: an anchor with a budget around it can sit below what `main` measures (a module 60 B over its anchor passes G10's `+128 B`), and a wall can sit far above it (the `vite-ssr` emitted wall was anchored at 14,396 B while the fixture emits 2,049). Measured against the anchors, every open pull request would record that gap as its own change, so with two open it would count twice: the first case loosens the limit, the second tightens it. The first simulated run of this design did exactly that, recording -12,347 B on the `vite-ssr` wall for a change that never touched it. Against the merge-base the gap stays out of every change file, the tree with both pull requests is held to `main`'s own headroom, and a Mac-measured change carries no Mac-to-Linux offset, since both of its measurements come from the Mac.
- Two pull requests that both `set`, `remove` or `append`-conflict on the same anchor (both add the same new runtime module, say) make reading the anchors fail with both file names. The later one runs accept again. Two `delta`s on the same anchor add up; that is the point.
- `pnpm anchors:fold` writes the applied anchors back into the anchor files, appends one `history` line per changed anchor with its reason, and deletes the change files. It changes no limit (its test proves the anchors read the same before and after), so it can run in its own pull request at any time; the files other open pull requests add are not touched. Fold when the directory holds about 20 files, or with the weekly upkeep. A test in the unit lane applies every committed change file, so a malformed or conflicting one fails `main`'s required checks, not a later run.
- The perf-guards lane uploads its measurement as the `perf-guards-measurement` artifact, stamped with the platform it was taken on, so a Linux number can be accepted from the CI runs that measured it: `gh run download <run> -n perf-guards-measurement` for this pull request's run and for the merge-base's, then `pnpm perf:guard:accept load "*" --from <this run's file> --base <merge-base's file> --reason "..."`. Accept refuses two measurements from different platforms.

**What still costs a round.** For G16 downloads on CI this paragraph no longer applies: see "How G16 judges downloads" below. Gzip is not exactly additive when two pull requests change the same file: the tree with both can measure a few bytes more or less than the sum of their two changes. In the merge queue on 2026-11-11, #598 recorded `+43 B` and #602 `+88 B` on the docs pages, each measured on `224ddbee3`; the tree with both measured `+138 B`, 7 B over the sum, and the queue ejected #602 though nothing in it was unrecorded. Over 42 merge-queue runs from 2026-10-30 to 2026-11-11 (31 pull requests that moved a page's download by at most 2 KB; each run's growth over its queue base compared, per site, with the same pull request's growth on its own CI run, 61 comparisons), the queue measured up to 48 B more than the pull request's own run, and 28 B or less in all but one.

So G16 lets a page download up to 48 B over its anchor (`loadDownloadCompositionBytes` in `scripts/benchmarks/perf-guards/config.mjs`). The allowance is measured against the anchor, not against the merge-base: the limit stays `main`'s anchor plus the recorded changes plus 48 B, so growth no change file records adds up across pull requests and fails once it passes 48 B in total; it cannot creep. Code run at load gets no composition allowance: its budget is only the measured swing of the lowest of three loads (`+256` chars). A tree more than 48 B over still fails, and the pull request accepts once more on a tree with both, which records its change against a merge-base that includes the first. A tree that measures less leaves the limit that many bytes above it until the next accept on that anchor; that headroom is how #595 passed its own run unrecorded (its merge-base `78ce0b3b2` measured 212 B under the docs home page's anchor), so a pull request still accepts what it adds even when G16 is green. Two other designs would need no allowance, and both were rejected: re-deriving the anchors from `main`'s measurement after each merge was rejected above, and checking raw (uncompressed) bytes instead of gzip would compose almost exactly but stop measuring what a reader downloads. The `fixture-builds` walls keep their 12 to 21 B margins, which already exist for gzip variance between runs. A pull request that moves a Linux-only G16 number still needs a Linux measurement of both trees: its own CI run's artifact for `--from`, and for `--base` the artifact of the merge-queue run that tested the merge-base commit (the queue's commit is the one that lands). When that run skipped the perf-guards lane because its inputs had not changed, the last run that did measure those inputs has the same numbers.

**Scope.** The perf-guard anchors and the `fixture-builds` runtime anchors and gzip walls use this from 2026-11-03, and the build-scale client module and whole-module compile counts from 2026-11-13. The music-player budgets, the other build-scale budgets and box byte walls change a few times a month and still edit their own files; they move onto the same ledger if they start to collide.

### How G16 judges downloads

**The problem.** On 2026-11-13 five approved pull requests left the merge queue on a byte or module count nobody had grown in that run: #645 (a `fixture-builds` wall, +9 B), #669 (+49 B against 48), #663 (+51 to +71 B), #674 (+60 B) and #648 (4,554 client modules against 4,553). Each cost a rebase, a fresh measurement and a full CI run, and held up the pull requests queued behind it.

Every limit was an absolute number: the anchor plus the recorded changes, plus 48 B. CI's measurement of `main` did not sit on the anchor; on `docs /` it moved between 144 B below and 98 B above it in one day. Below the anchor, a pull request could grow a page by that much, record nothing, and still pass its own run (#669 grew `docs /` by 78 B; #663 recorded 451 B on the accordion page and grew it by 695 B; #680 grew `docs /` by 46 B). The pull request queued next then paid for it: #674's own change measured 27 B over what it recorded, but `main` was already 33 B over after #680, so it failed at 60. The build-scale module count failed the same way: `main` measured 4,552 against a budget of 4,553, #659 added a module without recording it, and #648, which also added one, failed at 4,554. The full analysis and the replay are in `goals/async-dx/notes/T177-perf-anchors-compose.md`.

**What happens now.** CI judges a page's downloaded bytes against a measurement, not the anchor. Downloaded bytes are the same on every run of one tree, so the measurement of an earlier commit is a fact to build on:

- The reference is CI's measurement of the last commit that recorded a real change to the page's download: a change file entry for that page whose `jsGzipBytes` moves by a nonzero amount. A `0 B` entry, an entry that changes only executed characters, and an entry for a whole platform record nothing and move nothing.
- The limit is that measurement, plus every change recorded for the page since it (this tree's own included), plus 48 B (`loadDownloadCompositionBytes`, unchanged). A recorded change of N lets the page move by N. A recorded change landed ahead in the queue is inside its own measurement once it becomes the reference, so accepted changes never add up against each other.
- The 48 B is shared by every pull request since that record, not handed out fresh to each one: three pull requests that each grow the page 47 B fail on the second, with or without a `0 B` entry. It covers gzip composing recorded changes with each other and growth too small to record. The anchor's spare room no longer hides growth.
- Executed characters stay on the anchor with their 256-char swing. They move in steps of 107 to 331 chars between runs of one tree, so comparing one run with another would double the noise. For the same reason `perf:guard:accept load` records a page's executed change only when it moved past that swing: `load "*"` used to write ±107 to ±224 chars of noise into the anchors of pages the change never touched (#645 recorded +225 on two bench pages). A change file entry for one page moves only that page's limit.

The measurements come from the `perf-guards-measurement` artifacts (kept 14 days) of `ci.yml`'s merge-queue and `main` runs. After measuring, the guard runs `scripts/ci/perf-guard-baseline.mjs`, which walks HEAD's first parents (git history, at most 300), finds each page's reference commit from which commits recorded a nonzero download change for it, and downloads that commit's measurement. When the reference is the queue entry ahead of this one, still measuring, it waits for that run's perf-guards job, at most 10 minutes.

**When the reference cannot be read.** If the reference commit's measurement is missing (the wait ran out, the artifact expired, the run failed before uploading), or reading it fails (a `gh` error or rate limit), or no real record is within 300 commits, that page is judged by the anchor rule exactly as before this change: its anchor with every change file applied, plus 48 B. The baseline never steps back to an older measured commit instead, since an older commit can sit further above its anchor and give a looser limit. The log names the page and the reason (`G16 <page>: judged by the anchor rule: ...`). So a failed lookup is never looser than the old rule.

**What is still looser than the anchor rule.** A reference that measured above its anchor gives a limit that much above the anchor rule's. That gap is what recorded changes composed to, plus at most 48 B per real record of growth too small to record: each real record starts a new shared allowance. An absolute backstop against the anchor would close it, but would bring back the queue ejections this change removes; it is an owner decision, not taken here.

**Accepting a cost, in plain words.**

1. Your pull request grows a page's download. The perf-guards job says which page and by how much.
2. Download two measurements: your pull request's run and the merge-queue run of your merge-base (`gh run download <run> -n perf-guards-measurement`).
3. Run `pnpm perf:guard:accept load "*" --from <yours> --base <merge-base's> --reason "<what the bytes buy>"`. It records the difference for every page that moved.
4. Record every page your change grows, even by a few bytes. A page you leave out counts against the 48 B shared with every other change that left it out.
5. You do not need to accept again when another pull request lands first, unless both change the same code: your recorded change is added to the measurement of the last change recorded ahead of it.

### Why G16 measures the same code every run

**The problem.** On `main`, with no code change, merge-queue runs measured `bench /` at 11,665, 11,772, 11,889 and 11,996 chars and `bench /settings` at 11,631, 11,738 and 11,962, against a budget of 256. Pull requests went red or green depending on which value their run drew, and authors reran. A Mac measured the same build at one value every time. Per-load V8 coverage from the CI runners named two causes, both in the router's link bridge (`startFragmentNavigation` in `packages/router/src/vite/fragment-navigation.ts`):

- **A hover nobody made (224 chars).** Headless Chromium on Linux keeps its pointer at (0,0) and, once the page lays out, sends a trusted `pointerover` to the element there (the bench header). On 12 of 12 CI loads it arrived; whether the bridge's listeners were attached yet decided whether its `listen` handler and `anchorOf` (149 and 75 chars) ran. Other listeners ran on it every time: without the event CI measures 373 to 704 chars less per bench page than `main`'s runs did. A Mac gets no such event. Moving Playwright's mouse elsewhere first did not help: the new page still got the event at (0,0).
- **A modulepreload racing the load event (107 chars).** The bridge waits for the load event and then for every head modulepreload that has not landed. Unthrottled, the load event came before the last one (the swap module) in 22 of 24 CI loads of `/` and `/settings` and in 0 of 12 of `/records`, so the branch that adds a listener per pending link ran on some loads and not others.

**What happens now.** A G16 load (`loadWeight` in `scripts/benchmarks/perf-guards/measure.mjs`) opens its page `untouched`: a capture listener added before any page script stops the browser's pointer and mouse hover and move events (`pointerover`, `pointerenter`, `pointermove`, `pointerout`, `pointerleave` and their `mouse` twins), since the visit sends no input. It also runs at 4x CPU (`LOAD_WEIGHT_CPU_SLOWDOWN`, the cost model's CPU factor), where every preload landed before the load event in 36 of 36 CI loads. That makes the race rare, not impossible: the network and disk are not slowed, so a stalled preload can still arrive late. So a load counts only if every head modulepreload had arrived when its load event fired; one that had not is discarded with the reason "preload race lost, not a regression", loaded again, and counted as `preloadRaceLost` in the measurement. After 6 such loads on one page G16 fails, naming the page. This is not a retry of a failed check: the discarded load did not meet the condition the measurement is defined under, and its number is never compared with an anchor.

Ten CI jobs of one commit (run 44662591386, 30 loads per page) and the pull request's own run then measured every bench page at a single value per load: `/` 11,292, `/records` 11,308, `/settings` 11,258 chars. A Mac run of the same tree read the same three numbers. The bytes downloaded did not change. The Linux anchors were re-recorded once from those runs (`scripts/benchmarks/anchor-changes/ci-g16-deterministic.json`; `docs /` by an explicit entry, since accept drops moves under 256 as noise); the budget stays 256. The Mac anchors were not, and are stale (#954).

**Still moving.** All three docs pages still differ by 33 chars between loads of one build: `docs /` read 25,743 on at least one load in 8 of the 10 jobs (its lowest of three stayed 25,710), `/concepts/state` read 25,744 or 25,777 as its lowest of three, and `/ui/accordion` 24,502 in the proof jobs and 24,535 in the pull request's run. The cause is not found yet (#952). G14, G15 and G18 load their fixtures in their own browser contexts and still flip by the same 107 and 224 chars; they keep their 512-char budgets until they get the same treatment (#953). Each counted load's figure is kept in the measurement artifact as `executedRuns`, so a future flip shows which load moved.

### Unit CPU and memory budget

Each `unit` shard runs under `scripts/ci/unit-budget.mjs measure`, which records the CPU-seconds of the whole process tree it waited for (Linux `cutime` + `cstime`) and the tree's peak RSS, sampled once a second, and uploads them as a `unit-budget-shard<n>-attempt<n>` artifact. The `unit-budget` job then runs `unit-budget.mjs check` on the latest attempt of every shard against `scripts/ci/unit-budget.json`:

- GitHub hands out runners with different CPU models, and the same shard spent 543 CPU-seconds on an AMD EPYC 9V45 and 831 on an EPYC 7763. Before the tests, `measure` times a fixed JavaScript workload in one process per CPU at once (the fastest of three rounds in each, so shared cores slow it as they slow the tests), and the check scales each shard's CPU-seconds to the anchors' speed by that calibration. The calibration's own CPU is not counted.
- The calibration does not rank CPU models the way the suite does: against each shard's median, CPU-seconds over calibration CPU-seconds read 7-11% high on Intel Xeon 6973P-C, 6975P-C and 8573C and 9-11% low on AMD EPYC 9V45 and 9V74 (262 measurements, 89 runs), so run 43572444143, whose three shards all landed on Intel, read +22% on an unchanged suite. The check also divides by a factor per recorded CPU model, which `unit-budget.mjs models --from <run>... --reason "..."` fits from many runs' measurements. A shard on a model with no factor counts at factor 1 with its share of the CPU band widened to the ±20.4% measured before factors existed (`models.unknownMargin`), so a new runner model does not turn main red; the check prints a warning naming the refit command. Fit the model in once it has five samples. Changed factors invalidate the anchors and the margin, so the check fails until both are taken again with `accept` and `margin`. With the factors, the same 12 same-tree measurements that set a 20.4% margin spread 11.8%.
- On one CPU model, the suite follows only part of a calibration swing. The calibration is a few seconds of work timed once before the tests, and part of its swing is momentary: on EPYC 7763 the suite's CPU-seconds move 0.38 times as far as the calibration in log terms, on 9V45 0.51 and on Xeon 6975P-C 0.55, while on 9V74, whose slow hosts stay slow, they move 0.92 times as far (1,999 shard measurements from 684 runs, each compared with the same shard in its 8 nearest runs). Dividing by the whole calibration read a host that calibrated fast as heavy work: merge-queue run 44323217515 (#830) calibrated shard 3 at 0.881 against the 9V45 median of 1.082 and read +15.1%, and the rerun of the same commit read +4.6%. So `models` also records each model's median calibration (`models.calibrationS`) and that slope (`models.elasticity`), and the check divides by the median moved that share of the way toward the shard's own calibration. A model with fewer than 20 samples keeps its whole calibration. With this correction, the same 12 measurements spread 8.9%. Over 214 main and merge-queue runs, a run's total sits within 6.0% of its neighbours' median (it was 8.8% before), so a +12% change clears the 8.9% band.
- The gated numbers are the shards' summed scaled CPU-seconds and the largest shard's peak RSS. Vitest assigns files to shards by path, so adding a test file moves work between shards; the sum and the largest shard move only with real work.
- A run is compared with `main`, not with a fixed number. Before the check, `unit-budget.mjs main` downloads the measurements of `main`'s last 10 landed merge-queue runs that ran the unit lane: commits on `main`'s first-parent line whose green `merge_group` run uploaded `unit-budget-shard*` artifacts. `check --main` counts each of them exactly as it counts this run, and takes the median of their total CPU and of their largest shard peak. A number more than the noise margin above that median fails as over budget.
- The committed anchor is a ceiling. However far `main` has moved, no run may pass the anchor plus the margin, so a pull request can never add more than it could against the fixed anchor: where `main` sits below the anchor, the limit is `main`'s median plus the margin, which is lower; where `main` sits above it, the limit stays the anchor's.
- A number more than the margin below `main`'s median is a warning, not a failure. A pull request did not make `main` heavier than itself, and failing it for `main`'s stale anchor taught nothing: on 2026-11-21, 6 pull request runs failed only that way, after #985 lowered every shard's memory.
- When `main`'s median moves more than half the margin from the committed anchor, the check warns (`main moved: ...`) on every run, and `main`'s push runs warn in `carry-queue-markers`. A re-anchor pull request with an attribution table (which merged changes moved it, by test file) is then expected; the warning names the `accept` command over those 10 runs. Re-anchoring lowers or raises the ceiling, so it stays a reviewed decision with a reason.
- If fewer than 10 usable landed runs can be read (an API error, expired artifacts), the run is held to the committed anchor alone, with a warning, exactly as before this rule. That is never looser than the rolling comparison's ceiling.
- Why: with the fixed anchor alone, legitimate changes walked `main` toward one edge of the band (tests added since #896 for CPU, #985's memory win), and ordinary noise then pushed innocent runs out. Replayed over every run since #985 (memory, 121 runs) and #1019 (CPU, 72 runs) with the same margins: memory false failures 6 → 0; a +10% memory regression caught in 88 of 121 runs instead of 9, +12% in 115 instead of 38, because the stale anchor had left that much room. CPU false failures stayed 0. The one place the median alone is weaker: a +10% CPU regression is caught in 61 of 72 runs against the fixed anchor's 72, because `main` sat +1.6% above the CPU anchor, so the median's limit was 1.6% above the anchor's. The ceiling closes it: where `main` is above the anchor, the limit is the anchor's, and the rule as built (median and ceiling) catches 72 of 72, as the fixed anchor did.
- The margin is measured, not chosen: `unit-budget.mjs margin --from <run>... --reason "..."` takes every attempt of every shard in the given runs (at least three samples a shard, all on the same set of test files) and stores the largest deviation of a sample from its shard's median, with the samples, in the budget file.
- Anchors are Linux numbers from CI, never from a Mac: `unit-budget.mjs accept --from <run> --reason "..."` downloads that run's artifacts with `gh run download` and anchors each shard at its median over every attempt of the runs given. The reason says what the extra CPU buys, or which win the lower anchor records.
- The check runs only in a run whose unit lane ran; a lane skipped on its content hash measured nothing.
- The unit lane's green marker is saved only after `unit-budget` passes, and the `test` gate needs `unit-budget`. Until 2026-11-11 the check ran as the last steps of `test`, and the marker was saved once the shards passed: a red budget left a green marker behind, so re-running the failed jobs skipped the unit lane and the check and turned `test` green without a new measurement (runs 42977040110 and 42977235121). A failed sibling lane also stopped `test` before the check, so a memory regression went unreported until every other lane was green. As its own job, the check reports even when another lane fails, and after a red budget a re-run measures the unit lane again. `check-workflow.mjs` fails a workflow that saves the unit marker without waiting for `unit-budget`.

### Memory held outside the build slot

**The problem.** A shard runs two test files at once. Builds already take turns: `packages/router/test/support/build-slots.ts` gives a 16 GB runner one build slot, a `buildFixture` build takes it for one build, and an `inWorkerBuilds` file takes it for its whole run. A file that keeps a lot of memory without building through the slot did not take turns, so whichever build the other worker reached landed on top of it. In the 49 merge-queue runs from 2026-11-19 13:40 to 2026-11-20 07:58, shard 2's peak was always `render-order-sweep.test.ts` (2,066 to 2,220 MB, no slot) plus one build plus about 1.2 GB of vitest's main process, the shared Chromium and pnpm. Before #910 that build varied with timing and the largest shard peak read 3,822 to 4,347 MB; since #910 it was almost always `storage-key-across-modules.test.ts` (1,165 to 1,332 MB) and the peak read 4,165 to 4,550 MB. One batch on one commit read 4,177, 4,397, 4,406 and 4,550 MB, and run 44694611174 left the queue at 4,550 against a 4,147 MB anchor.

**What happens now.** `unit-budget.mjs measure` names the slot folder (`MARKLESS_BUILD_SLOTS_DIR`). At each sample it reads which workers hold a slot, both before and after it reads the processes, and counts a file as holding one if it did at either read. Each file's peak over the samples where it held none is uploaded as `fileUnslottedPeaksMb`, with every file over 256 MB, and the seconds a slot was held for a whole file as `wholeFileSlotS`. Files listed under `slotHolders` in `scripts/ci/heavy-tests.json`, each with its measured peak, the run and why, hold the slot for their whole run (`scripts/ci/in-worker-build-slot.ts`), so no build overlaps them. The slot frees in `afterAll`, just before the worker exits, so a build can start while the worker's memory is still resident.

**The line and what it guarantees.** The line is 1 GB outside the slot (`SLOT_HOLDER_MB`). It is not derived from the RSS band, and it does not keep a shard inside it: the largest file that holds the slot (`separate-client-build.test.ts`, 2.3 to 2.6 GB) plus the base processes (1.2 to 1.7 GB) already come within about 400 MB of the band's top of 4,475 MB, so one file under the line beside it can still push a shard over. What it guarantees: no two files over the line run at once, and none of them runs beside a slotted build. The line is a cost choice: listing a file makes builds in the other worker wait for its whole run.

**When the check fails.** `unit-budget.mjs check` reads the files this change adds or modifies (`git diff --name-only --diff-filter=AMR` against the base the `changes` job chose).

- A file over the line that the change did not touch is reported, as a warning annotation and in the job summary, with the count of such files; it never fails the run. A pull request is never ejected for a file it did not touch.
- A touched file fails only above 1,761 MB (`SLOT_HOLDER_FAIL_MB`, 1.72 times the line). Across this change's first three CI runs (44705540466, 44711088992, 44721518685), one unlisted file's peak outside the slot moved by up to 1.72 times between runs (34 files; median 1.16, 90th percentile 1.49). A file that read under the line in one run has not read over 1,761 MB in another. The check reads one run, which measures each file once, so it uses this margin rather than a median.
- Every unlisted file measured over 1,182 MB is listed now: the 90th-percentile swing (1.49 times) could carry it past the fail line.
- A listed file whose whole peak in a run was under 595 MB (`SLOT_HOLDER_STALE_MB`, the line divided by the same 1.72) is reported as stale, and fails when the change touches it.
- Whole-file holds may cover at most half of a shard's wall time (`SLOT_HELD_SHARE`), so the list cannot grow until a shard is serial. Each shard's share is reported on every run; over the ceiling it fails only when the change touches `scripts/ci/heavy-tests.json`.

**What it cannot see.** In CI, `launchBrowser` connects to the one Chromium that global setup starts (`scripts/test-utils/browser.ts`). Its processes are children of vitest's main process, so their memory is charged to no test file and counts toward no file's peak; that group read 1,849 to 2,537 MB at its own peak. A file whose pages use a lot of browser memory never trips the line (#995). The changed-file rule also sees only the test file itself: a change to a helper or fixture that makes an unchanged test heavier is reported, not failed.

**Measured.** The first run with the measurement and an empty list (44705540466) flagged 15 files, 1,400 to 2,094 MB outside the slot; they are the list. Most build through `execFile` or a demo lock rather than the slot, or serve their app and drive their own Chromium after the build. The next run (44711088992) measured the largest shard peak at 4,001 MB (shard 1, `separate-client-build.test.ts`, which already held the slot), and shard 2's at 3,765 MB: the sweep at 2,318 MB beside a 198 MB file. Summed CPU at the anchors' speed was 2,837 CPU-s against 2,825 in the run before (+0.4%, anchor 2,731, band ±8.9%). Shard wall times were 427, 579 and 404 s against 445, 376 and 488 s, on different CPU models, inside the 296 to 705 s range of the 49 queue runs.

### Node's compile cache

Node can keep what it compiled on disk and reuse it in the next process: V8's code cache for each module, and the output of stripping TypeScript types. The root Vite config turns it on (`scripts/test-utils/node-compile-cache.ts`) in `node_modules/.cache/node-compile-cache`, and sets `NODE_COMPILE_CACHE`, so every test worker, fixture-build child and bundler build worker a test run starts uses the same directory. `NODE_COMPILE_CACHE=<dir>` picks another directory and `NODE_DISABLE_COMPILE_CACHE=1` turns it off.

A stale entry cannot change behaviour. Node checks every entry against a hash of the source it was made from and against a hash of its own data, and drops it on a mismatch; it keeps one subdirectory per Node release, architecture and V8 flags, so two Node versions never share an entry. Checked on Node 24.22.3 with `NODE_DEBUG_NATIVE=COMPILE_CACHE`: a `.ts`, an `.mjs` and a `.cjs` file rewritten with the same name, byte length and modification time were each reported as `code hash mismatch` and ran their new code, and cache files overwritten with garbage were reported as `cache hash mismatch`, recompiled and rewritten. Writes go to a temporary file first and are renamed into place, so parallel workers never read half a file.

On this Mac (8 workers) the whole node project spent 1,750 and 1,765 CPU-seconds without the cache, 1,497 starting from an empty one (fixture-build children reuse what earlier processes in the same run wrote) and 1,442 and 1,439 with a warm one. A full run writes about 4,100 entries (74 MB) and each later run adds about 1,000 for files a run creates under new paths; Node never prunes, so the main process empties the directory once it passes 16,384 entries.

On CI the unit shards start warm only if they restore a cache, and only a run on `main` can save one that pull request and merge-queue runs may read. `ci.yml`'s push run skips the unit lane the merge queue already ran, so `node-compile-cache.yml` runs each unit shard's test files on `main` once a day, and again when the lockfile or the Node release changes, and saves `node-compile-cache-<os>-node<version>-shard<n>-<lockfile hash>-<day>`. Its tests only load modules, their results are not a check, and it installs no browsers. The daily sweep in `cache-cleanup.yml` keeps the newest entry per shard and lockfile. Even without a restored cache, the processes of one unit run reuse what earlier ones compiled, which cut the unit lane's CPU by about 12% (re-anchored 2026-11-19 from run 44546975882). The `unit` job does not restore it yet: it starts cold until a follow-up change restores the cache and re-anchors the unit CPU budget on warm measurements, which can only be taken once this workflow has saved a cache on `main`.

### Heavy unit tests

`scripts/ci/test-placement.mjs`, in the `agent-files` job, lists the node project's test files through Vitest and walks their imports on the yuku project graph (`packages/analyzer/test-support/test-placement.ts`, parsing only the modules the tests reach). A test whose imports reach an entry in `scripts/ci/heavy-tests.json` (the router fixture-build helper, the browser launch and built-server helpers, a Playwright browser type, Vite's build API) must be listed under `tests`; a listed test that no longer reaches one fails as stale. A script a test spawns by `resolve(import.meta.dirname, '<file>')` counts as an import. A test that is heavy by a route no import shows, such as running `pnpm build` or `vp pack` in a child process, is listed under `declared` with the reason. `node scripts/ci/test-placement.mjs --write` rewrites `tests` from the graph for review; `--json` prints the import chain that makes each test heavy.

A router or bundler test builds its app through `buildFixture` (`packages/router/test/support/fixture-build.ts`), a child process that exits after the build and takes one of a few build slots (one on a 16 GB CI runner), because Rolldown keeps a build's memory until its process exits and two builds at once pushed unit shards past their memory budget; the same check fails a test whose value imports reach Vite's `build` or `createBuilder` unless it is named with its reason under `inWorkerBuilds` in `scripts/ci/heavy-tests.json`. A named test needs the build in its own process (process ids, in-process compiler state, in-memory output), and `scripts/ci/in-worker-build-slot.ts` makes it hold a build slot for its whole run so it never overlaps another build. A test that runs a production build as a command (`vp build`) wraps it in `withBuildSlot` from the same helper: the composition grid's `vp build` (1.6 to 1.9 GB) ran beside `migration-defects.test.ts`'s fixture build (about 2 GB) and pushed shard 2 to 4561 and 4788 MB (merge-group runs 43638091459 and 43639298678).

### Build warnings

The `build-warnings` job (`pnpm build-warnings:guard`, `scripts/ci/build-warnings.mjs`) builds the docs site and the demo apps and fails on any line a build prints to stderr; `packages/cli/test/starter-build.test.ts` holds every starter's `vp build` to the same rule. Bundler, Vite, Nitro and Node warnings all go to stderr. Rolldown's `[PLUGIN_TIMINGS]` report is the one block it skips: it reports how long plugin callbacks took, not a defect. Each `ALLOWED_WARNINGS` entry names one build and the one-line reason its warning stays. There is no entry today: the docs site's chunk-size warning is gone because the bundler cuts a navigation or deferred pack at Vite's `chunkSizeWarningLimit`, and a constant slice bigger than that loads as its parts. Fix a warning where it starts; do not silence it with `/* @vite-ignore */`, a raised `chunkSizeWarningLimit` or a disabled Rolldown check unless that line can be written.

The same job then reads every JavaScript file and inline script each build wrote for the browser (`scripts/ci/browser-output-scan.mjs`; `.output/public`, or `dist` without `dist/server`) and fails on Node-only code: an import of a Node built-in, a use of `process`, `Buffer`, `global`, `__dirname`, `__filename` or `require` outside a `typeof` check, or Rolldown's stand-in for a `require()` it could not bundle. The starter build test runs the same scan. It is a second check behind the bundler's own `MARKLESS_NODE_IN_BROWSER` build error, so it has no allow list: fix a finding by moving the shared value into a module that imports nothing from Node.

### The Actions cache is a budget

Restoring a cache counts against the repository's cache egress limit. On 2026-10-23 it ran out: restores failed with `Egress is over the account limit`, and pnpm restores in unrelated jobs stalled until the job was cancelled. Most of the traffic was restores, not saves:

| Restore                               | Size         | Jobs per run | Per run      |
| ------------------------------------- | ------------ | ------------ | ------------ |
| pnpm store, screen-reader family jobs | about 215 MB | 102          | about 22 GB  |
| pnpm store, CI jobs                   | 219 MB       | about 25     | about 5.5 GB |
| Playwright Chromium and WebKit        | 394 MB       | 14           | about 5.5 GB |
| Playwright system packages            | 119 MB       | 13           | about 1.5 GB |

What changed, and the rule going forward:

- The screen-reader family jobs install from the npm registry with no pnpm store cache. Their virtual lane reads with the runner's Chrome and downloads no browser.
- Box lanes whose boxes only use witness's browser (router, both music players) restore no Playwright browser or system packages: witness drives the runner image's Google Chrome. `boxes-bundler` (its analyzer measurement), `website-boxes` (the mug studio box), `demo-boxes`, `perf-guards`, `unit` and `browser` launch Playwright's Chromium and keep the restore.
- `prepare-playwright` looks the browser cache up instead of restoring it, and skips the pnpm store cache.
- No lane needs `prepare-playwright`: it fills the caches beside the lanes, and on a miss (a Playwright bump) each lane installs its own copy and restores the newest older system-package entry. Waiting on it cost a merge group a second runner queue, 12 minutes on 2026-10-27.
- `cache-cleanup.yml` deletes a pull request's caches when it closes, and a daily sweep deletes caches of closed pull requests and deleted branches and every main tool cache but the newest per key. Dry run against 2026-10-23: 232 of 722 entries, 6.6 of 10.6 GB.
- A new cache step needs a reason it pays for itself: what one restore costs, how many jobs restore it per run, and what it saves over downloading. A cache restored by a large matrix is the first suspect.

### Merge queue settings

The `main` ruleset's merge queue builds at most 2 groups at once (`max_entries_to_build`), merges up to 10 pull requests per group (`max_entries_to_merge`), and waits 1 minute for a group to fill (`min_entries_to_merge_wait_minutes`). Until 2026-10-28 it was 4, 5 and 5 minutes. With 25 pull requests queued that day, four groups each ran about 24 jobs and competed for the same 60 runners with pull request runs and Ecosystem CI on `main`: the oldest entry had waited 15 hours, and finished groups sat 20 minutes or more waiting for a runner for their last two jobs. Fewer groups in flight get their runners sooner, and larger groups merge more pull requests per tested run. The cost is that a red group holds back more pull requests while the queue splits it to find the culprit. Change these numbers only with a measured queue time before and after, recorded here.

### Self-hosted merge-queue runners (trial)

The org's 60 hosted runners are shared with every repository, and on 2026-11-20 a green merge-queue run took a median of 58 minutes, about 45 of them waiting for runners: the slowest lane waited a median of 31 minutes, then `unit-budget` and `test` each waited again (`test` a median of 12). The owner's Mac minis can take merge-queue jobs off that pool. Two repository variables route them, and with neither set every job runs on `ubuntu-26.04` as before:

- `MERGE_QUEUE_RUNNER`: the runner label (`markless-merge-queue`). Set, it moves the jobs after the lanes (`unit-budget`, `save-lane-markers`, `test`, `benchmark-guard`) to the minis. They read artifacts and caches and run no host-dependent test, and they hold two of the three runner waits on a merge group's path.
- `MERGE_QUEUE_RUNNER_JOBS`: a space-separated list of further jobs to move, from `agent-files`, `typecheck` and `changes`. Each takes a runner but none sits on the critical path, so moving them frees hosted runners for the lanes.

Only a `merge_group` run can select the label: every routed `runs-on` is `github.event_name == 'merge_group' && ... || 'ubuntu-26.04'`, and `check-workflow.mjs` fails any other non-hosted `runs-on`. A pull request can edit both, so the control that holds is on the runner: its job-started hook (`ACTIONS_RUNNER_HOOK_JOB_STARTED`, outside the repository) fails every job that is not a `merge_group` run of this repository's `ci.yml` on a `gh-readonly-queue/main/*` branch, before any step runs. The jobs that stay hosted cannot move without changing what they check: `unit-budget.mjs` refuses unit measurements taken off linux-x64, and the browser, box, perf and benchmark lanes depend on the runner's browsers and timing.

Each mini runs at most three jobs at once, one per non-admin user (`ghrunner1` to `ghrunner3`), each a just-in-time runner that takes one job and is removed; between jobs the user's processes, crontab, temporary files and home folder are wiped. The routed jobs do not use the pnpm store cache, because a macOS store saved from every queue branch would evict the Linux caches (the repository's cache sat at 9.4 of 10 GB). The setup and its limits are in the runner recipe (`~/handoff/local-runners-recipe.md` on the minis).

A job for a self-hosted label waits up to 24 hours for a runner, so a dead mini would hold every group until the queue's 240-minute timeout. `stale-queue-runs.yml` cancels a merge-queue run with a job that waited more than 15 minutes for a self-hosted runner, so the queue drops the entry and rebuilds the rest; unset `MERGE_QUEUE_RUNNER` to send new runs back to hosted runners, then requeue the dropped pull requests.

### Screen readers

`screen-reader.yml` has three lanes. Pull requests that can change what is heard run only the virtual reader (`virtual`, Linux, every family split across three jobs; it was one job per family until 2026-10-28, 44 jobs a pull request that spent 33 s of each 55 s on install and type-check). NVDA (Windows) and VoiceOver (macOS) read `main` every night and on dispatch, and the release cut refuses unless the newest nightly run it contains passed (section 8, step 1). On 2026-10-26 the two real readers ran 2,644 jobs on pull requests in one day, about 37,000 Windows and macOS runner-minutes, over 40% of everything the org ran, and every other workflow's jobs queued behind them. To hear a branch with the real readers before it merges, run `gh workflow run screen-reader.yml --ref <branch>`.

### The VoiceOver lane (parked)

`voiceover` in `screen-reader.yml` is advisory (`continue-on-error`). Since #150 it reads 12 or 13 of 29 families green on the `macos-latest` (macOS 26) image, up from 2 to 4. A redesign of the real-reader driver is parked; this records where the rest fail and the options, so the next attempt starts from evidence. The traces are in the logs of runs 39890507893, 39892233837, 39896946755 and 39904970834, which log every phrase.

The rest fail in four ways:

1. **Runner setup.** `guidepup/setup-action` sometimes fails with "Unable to write to the user TCC.db - SIP might not be disabled" or "Failed to enable Do not disturb mode": 1 to 3 families a run, a different set each time. This is the runner image, not the families.
2. **Speech after a focus move is not captured** (menu, modal, drawer, select, menubar). After Enter opens a surface and the family moves focus, `lastSpokenPhrase()` returns `""`: guidepup records only speech that follows one of its own commands, and VoiceOver's focus-following announcement is not one.
3. **Keys go to the page's focus, not VoiceOver's cursor** (buttongroup, colorpicker, crop, rating). The transcript walks the cursor with `next()` and then presses a key; on this runner keyboard focus does not follow VoiceOver's cursor, so the key reaches whatever was focused before.
4. **Containers VoiceOver steps over** (toolbar; tabs, editable and tour time out or miss a phrase for the same kind of reason). VoiceOver treats a toolbar as one item and needs its interact command to enter it.

Options, cheapest first:

- **A. Leave it advisory and stop here.** NVDA and the virtual reader already gate the same transcripts. Cost: the VoiceOver job stays mostly red and stops being read.
- **B. Give `RealDriverSpec` VoiceOver-only hooks and keep the shared transcripts.** `focusCursor` would run "move keyboard focus to VoiceOver cursor" before a key, only after a walk (fixes 3). `speakFocus` would run "move VoiceOver cursor to keyboard focus" with capture, only after a family moved focus itself (fixes 2). `enter` would run `interact()` on a container (fixes 4). A first version of `focusCursor` and `speakFocus` was tried in #150 and reverted: it broke the slider transcript (ArrowRight left the thumb at 50 where 41 was expected), and the cause was not established. Start by reproducing that on one family. Cost: a driver change plus one VoiceOver CI run per family to check it.
- **C. Separate VoiceOver transcripts** for the families whose interaction model differs (menu-like surfaces, toolbar, composite widgets), and keep the shared one elsewhere. Cost: two expectations to maintain per such family.
- **D. Move the lane to a self-hosted Mac** where TCC and Do Not Disturb are set once by hand. This only removes failure 1.

Recommendation: B, then C only for whatever B leaves red, with A as the state until someone owns it.

## 8. Cutting a release

Markless releases **minor versions only**: 0.6.0, 0.7.0, and so on. There are no patch releases. A fix ships in the next minor, so the way to ship a fix sooner is to cut the next minor sooner. No script or workflow accepts a release type; the next version is always the current one with the middle number raised by one.

### One click

Run `gh workflow run release.yml --ref main -f mode=cut` (or in GitHub: **Actions → Release → Run workflow** on `main`, mode `cut`). Nothing else is needed: no version, no confirmation phrase, no local step. The cut lives in `release.yml` itself because npm's trusted publishing checks the filename of the workflow that was dispatched; a separate workflow calling `release.yml` would be checked as itself and refused. The run:

1. Refuses to start unless it was dispatched on `main` and the checkout is clean. It then walks `main`'s first-parent history back from the head, no further than the current release, and picks the newest commit whose push CI run finished green with every check `main`'s ruleset requires coming out of that run. That commit is what gets released, and the log says which one it is and why each newer commit was passed over (still running, replaced by a newer push, or red). It refuses only when no commit since the last release is green. A burst of merges, or a red head, no longer blocks a release.
   Before anything is pushed, `scripts/release/reader-gate.mjs` finds the newest nightly or dispatched `screen-reader.yml` run on `main` whose commit the release contains, and refuses unless it passed and is under 72 hours old. NVDA and VoiceOver read `main` nightly instead of every pull request (see "Screen readers" in section 7), so this is where their verdict blocks. A refusal names the command that starts a fresh run.
2. Bumps the root `package.json` to the next minor with `bumpp`, then `scripts/release/sync-version.mjs` moves every published package to the same version. Packages marked `"private": true` are skipped.
3. Writes the new section at the top of `CHANGELOG.md` with `pnpm release:notes --changelog`: the `feat`, `fix` and `perf` commits since the last tag, grouped by the package their scope names, with internal ids removed and a link to every commit since the last release.
4. Commits `chore(release): vX.Y.0` as `github-actions[bot]` on top of that green commit. The commit runs the normal pre-commit hook (lint and CI's fast jobs), so the release commit passes the same checks as any other commit. Nothing is tagged yet: the tag goes on the commit that lands on `main` (step 5).
5. Lands the release on `main` through `main`'s merge queue, then tags what landed. `main` is protected by a repository ruleset named `main` that requires the `test`, `typecheck` and `agent-files` checks from GitHub Actions and accepts changes only through a merge queue that squashes each pull request into one new commit. So the release commit itself never reaches `main`: the commit that lands is the queue's, and that is the commit the tag and the publish use.
   First the release commit is verified. The cut pushes it to a temporary `release/vX.Y.0` branch (unprotected) and starts ecosystem CI (section 9) on it without waiting. Then `scripts/release/inherit-ci.mjs` diffs the release commit's tree against the green commit's tree. When the only differences are the top-level `"version"` of `package.json` files (each manifest is parsed and compared field by field with `version` removed) and `CHANGELOG.md`, with no file added, deleted or changing mode, and that commit's push CI run is still a green `ci.yml` run on `main` with every required check in it, running `ci.yml` again would test a tree CI already passed. So the cut posts each required check on the release commit as a commit status, `success`, linking that run and naming it in the description (`Inherited from CI run <id> on <commit>: same tree but versions and CHANGELOG`). Otherwise it posts nothing and runs CI: it opens a pull request from the branch into `main`, approves exactly that pull request's waiting `pull_request` CI run (it checks the run's event, commit and branch first), waits for the full `ci.yml` to finish, and `scripts/release/required-checks.mjs` confirms each required check passed on that commit in a `pull_request` run. As with any merge into `main`, only the required checks decide: on 0.9.0 the non-required `package-manager-matrix` job timed out on an npm install in the release pull request's run, which failed the whole cut.
   Then `scripts/release/land.mjs` opens the release pull request if CI did not already, adds it to the merge queue, and watches it. The queue builds a commit for it: the release's changes squashed onto `main`, or onto the pull requests queued ahead of it. GitHub starts no workflow for an event the workflow's own token causes, so that commit gets no CI run of its own; on 0.10.0 it sat in the queue for 4 hours until the queue dropped it. Instead `land.mjs` gives it the required checks the same way: once that commit differs from its parent only in versions and `CHANGELOG.md`, every release package in it is at the new version, and the parent passed every required check in a green `ci.yml` run (a push to `main`, or the merge queue's run for the pull request ahead), it posts the inherited statuses on it. If the queue rebuilds the commit (a pull request ahead failed), it checks the new one. When the pull request merges, `land.mjs` confirms `main` contains the commit that landed and that it is the one it verified, and creates the annotated tag `vX.Y.0` on it. The tag message records the commit the release was cut from (`Cut from <sha>`), and the next cut starts its changelog section there, so commits that landed while the release waited in the queue appear in the next release's notes. Then the cut pushes the tag and deletes the temporary branch.
   If the pull request leaves the queue without merging, or has not merged within 100 minutes, `land.mjs` takes it out of the queue and nothing is tagged or published; run the cut again. The cut never pushes to `main` itself, never uses `--admin`, and never pushes the tag before `main` contains its commit. Before any of this, `required-checks.mjs --names` (also run in `cut-dry-run`) confirms every required check name is a job in `ci.yml`, so a renamed job fails the cut at the start instead of at the end.
6. The `release` job, the same job that has always published, checks out the tag and publishes it: it builds, checks the tarballs, publishes with npm trusted publishing and provenance, and waits up to 20 minutes for npm to show every package with its provenance attestation (npm answers a large upload with "Your package is being processed" and took 13 to 14 minutes to show `@markless/core@0.6.0` and `@markless/compiler@0.7.0`). A rerun does not publish a package npm already took but is still processing: npm answers that with `E409 Cannot publish over previously staged version`, and `publish-workspace.mjs` then waits, up to 20 minutes, for npm to show it. A publish the registry answers with something that says nothing about the package is retried within the run, up to 4 attempts per package, 15, 30 and then 60 seconds apart. That covers `E401` and `E404` on the upload (npm's answers to an OIDC exchange it did not accept), and `E429`, `E502`, `E503` and `E504`. Each npm run trades a new OIDC token, and before each retry the package is looked up in case the failed upload landed anyway. On 0.6.0 one package got `E401 token is invalid` between packages that published with the same trusted publisher. 0.9.0 needed three publish runs: `E503` on `@markless/typescript-plugin`, then `E401` on `@markless/vitest-browser` and `E404` on `@markless/web`. Any other failure, or the fourth failed attempt, stops the run. It is the only job with `id-token: write`; steps 1 to 5 run in the `cut` job, which cannot publish.
7. The `announce` job creates the GitHub Release `vX.Y.0` from the new changelog section and marks it latest. It also runs after a successful manual `publish`, taking the notes from the tag's own `CHANGELOG.md` section (`scripts/release/changelog-section.mjs`), so a release finished by a publish-mode rerun gets its GitHub Release too. It marks that Release latest unless the publish used a dist-tag other than `latest`.

Expect about 20 to 25 minutes on GitHub's runners when the release commit inherits its CI run and the merge queue is empty: about 2 minutes of setup, 8 to 12 for the pre-commit hook in step 4 running CI's fast jobs on one runner (measured on the 0.8.0, 0.9.0 and two failed cuts), a minute or two for the queue to build and merge the release in step 5, and 7 to 20 for the build, publish and the wait for npm to show every package in step 6 (0.8.0 took 7). A pull request already in the queue adds the rest of its CI run, because the release lands after it. A release commit that cannot inherit adds the full CI run back: 17 to 25 minutes measured on the 0.8.0 and two failed cuts. The commit hook is never skipped.

The manual `dry-run` and `publish` modes still work as before for a version that is already committed, except that a publish now runs only on the commit tagged `v<version>`.

If the run stops after step 5, run it again. The tag then exists without a GitHub Release, so the cut finishes that release (publishing whatever is missing, then creating the Release) instead of cutting the next one; it accepts the release commit when either its own latest CI run is green or the inherited statuses cover every required check. If it stopped after the release landed on `main` but before the tag was pushed, the rerun finds the `chore(release): vX.Y.0 (#N)` commit on `main`, tags it, and finishes the same way. If it stops before the release lands, nothing is released: the next run first takes any open `release/v*` pull request out of the merge queue and closes it, then starts the same version again.

`main` may carry a release whose tag it does not contain: 0.10.0 was tagged on its release commit, which never landed, and the same change reached `main` later as a separate squashed commit. The cut handles both shapes: the newest release is the tagged commit when `main` contains it, and otherwise the commit where `main`'s root `package.json` took that version. Published tags are never moved.

### Pushes to `main`

CI on `main` runs one run at a time. A running run is never cancelled; while it runs, a newer push waits, and an even newer push replaces the waiting one (GitHub keeps one waiting run per concurrency group). The replacing run tests the whole tree, so no change goes untested: every lane is content-hashed, and the benchmarks compare against the last `main` commit whose CI passed, not against the previous push, so commits whose own run was replaced are still benchmarked. Running every push separately would give each commit its own result, but on 2026-10-22 a code run took about 56 runner-minutes and individual jobs already waited up to 24 minutes for a runner, so six merges in a burst would queue about 340 runner-minutes ahead of pull requests and the next release; the cut no longer needs the head's run, so that cost buys nothing a release needs.

### Rehearsing

Dispatch with `-f mode=cut-dry-run`, or run `pnpm release:cut --dry-run` locally. Both do steps 1 to 4 for real, including the commit and its hooks, in a throwaway copy of the checkout, then run the checks the `release` job runs before publishing (`pnpm build`, the publish-readiness sweep, the tarball checks and `pnpm publish --dry-run` for every package). They do not create the tag, push, publish, or create a GitHub Release. The drafted changelog section is printed (and shown in the run summary on GitHub). Locally, a dry run on a branch other than `main` finishes all the steps and then exits with code 1, listing what the real cut would refuse.

### One-time setup

The `main` ruleset (Settings, Rules, Rulesets, `main`) replaced classic branch protection with the same rules: it targets the default branch, blocks deletion and force pushes, requires the three checks from GitHub Actions without requiring the branch to be up to date, and lets repository admins bypass (classic protection did not enforce admins). `required-checks.mjs` reads the required checks from the ruleset and from any classic protection. No job in `release.yml` reads a secret.

Why the CI run comes from a pull request: the ruleset does not count required checks from a `workflow_dispatch` CI run. The 0.6.0 and 0.7.0 cuts dispatched `ci.yml` on the release branch, all three checks passed on the release commit, and GitHub still refused both the workflow token's push (`GH013 ... 3 of 3 required status checks are expected`) and the pull request merge (`the base branch policy prohibits the merge`); the pull request's check list did not show the dispatched run's checks at all. A test on scratch branches, under a temporary ruleset with the same three required checks, reproduced both refusals, and then, with the checks coming from an approved `pull_request` run instead, the workflow token's merge and its fast-forward push were both accepted. GitHub refuses the GitHub Actions app as a ruleset bypass actor, so nothing bypasses the ruleset.

Why inherited commit statuses count: on 2026-10-22 a workflow on a scratch branch, under a temporary ruleset requiring one context from GitHub Actions (app 15368), checked this with the workflow token ([run 39735539121](https://github.com/compiled-run/markless/actions/runs/39735539121)). A fast-forward push with no status was refused (`GH013 ... Required status check "inherit-probe" is expected`) and accepted once the token posted a `success` status with that context; a pull request merge with a merge commit onto a branch that had moved on was refused, then accepted once the pull request's head had the status. The ruleset and the scratch branches were deleted afterwards.

The cut needs "Allow GitHub Actions to create and approve pull requests" turned on in the `compiled-run` organization's and this repository's Settings, Actions, General, Workflow permissions (both are on). The ruleset requires no reviews, so the approval half of that setting is unused. No job in `release.yml` reads a secret, and no deploy key is used (deploy keys are disabled for the organization).

### Keep `main` releasable

Because a release is one click from whatever `main` is, `main` must always be releasable. Merge each fix as soon as its own checks pass, rather than batching fixes into one large push. A red `main` blocks the release cut as well as other pushes (see section 5).

### Bringing back the held packages

`@markless/ui`, `@markless/icons` and `@markless/ui-tools` are marked `"private": true`, so releases skip them. `@markless/icons` and `@markless/ui-tools` have never been published, and npm only lets a workflow publish a name that already exists. To bring them back (needs the owner's npm login and two-factor device, once):

1. Remove `"private": true` from `packages/headless/icons/package.json`, `packages/headless/tools/package.json` and `packages/headless/components/package.json`. Do this first: `pnpm release:trust --only` refuses a package that is still private. Their `publishConfig` already exists, so `verify-packed-manifests.mjs` has been checking their tarballs on every release.
2. Claim the two new names with a placeholder: a bare `package.json` at version 0.0.1 for each, published by hand (`npm publish --access public` in `/tmp/ml-bootstrap/icons` and `/tmp/ml-bootstrap/ui-tools`).
3. Attach the trusted publisher to all three: `pnpm release:trust --only @markless/icons`, `pnpm release:trust --only @markless/ui-tools`, then `pnpm release:trust --check`.
4. Merge the change from step 1 and cut the next release as usual. The cut moves the three packages to the release version with everything else. Packages publish in folder order, so `@markless/ui` goes out a moment before its two dependencies; if the run stops between them, run the cut again and it publishes the rest.

## 9. Ecosystem CI: the migrated sites

Markless's own suite passing does not show that real apps still work. The chunked page swap in 0.8 broke the page scripts of the shadcn-admin port, and an idle handler started 1.5 MB of JavaScript at load on its `/settings/account`; both were found by the port after the release. [compiled-run/markless-ecosystem-ci](https://github.com/compiled-run/markless-ecosystem-ci) turns the sites ported by markless-migrate into a regression suite, as vite-ecosystem-ci does for Vite: each suite builds one site against Markless packed from a commit, runs its build, and runs `markless-migrate check` on a sample of its routes against a capture of the old site, with no live network. The result is compared with main's last nightly result failure by failure, so a red that main already has (a known red, listed with its owner) is not counted; a new failure, a failed build, a route that could not be checked, or more JavaScript at load (over 2 KB and 5%) is.

**It never blocks anything.** No ruleset requires it, and the release cut does not wait for it. It notifies instead, every time a run on `main` or on a release commit finds a regression:

1. It comments on each merged pull request that landed between the commit main's baseline was recorded on and the commit it checked (found through the commits API), with the failing suites, routes and a link to the run.
2. It opens one issue labelled `ecosystem-ci` that mentions @thejackshelton, or adds a comment to the one already open.
3. It closes that issue, with a comment, on the next clean run on `main`.

- **`main`, every three hours:** the per-PR sample runs on `main`'s head when it moved since the last scheduled run. It ran on every push until 2026-10-27: 19 runs and about 7,600 runner-minutes on 2026-10-26, while pull request jobs queued for runners. A regression still comments on every pull request merged since main's baseline, so batching the commits changes when it reports, not who it names.
- **On a pull request:** a maintainer comments `/ecosystem-ci run`, or `/ecosystem-ci run shadcn-admin realworld` for some suites. `.github/workflows/ecosystem-ci.yml` builds the pull request's commit, runs each suite in its own job, posts the results table on the pull request and sets an `ecosystem-ci` commit status, which no ruleset requires. Run it on any change that can reach what a site ships: the bundler, the router, the runtime, `web` or the compiler.
- **Dispatch:** `gh workflow run ecosystem-ci.yml -f ref=<commit> [-f pr=<number>] [-f suites='a b'] [-f lane=full]`.
- **Release:** the release cut dispatches it on the release commit right after pushing the release branch and goes on without waiting. The GitHub Release notes link the run and say what it found (or that it was still running); a regression notifies as above.
- **Nightly:** the ecosystem repository runs every route of every site on `main` each night, opens an issue labelled `ecosystem-regression` there on new reds, and stores the night's results as the baseline pull requests compare with.
- **Locally:** `node scripts/ci/ecosystem-ci.mjs run shadcn-admin` fetches the ecosystem repository into `.ecosystem-ci/` and runs one suite against this checkout (`--route /users` for one route).

A sampled run builds Markless once and checks 22 routes of 8 sites in 18 parallel jobs: 20 to 25 minutes to the table, about 150 runner minutes (measured 2026-10-21; per-suite times are in the ecosystem repository's README). htmx-org and the migrate demo are not run until their ports move to Markless 0.8, whose TSRX changes they do not build with.

No secret, GitHub App or personal token is involved. The ecosystem repository is public, so the workflows check it out without a token; the jobs that build pull request code get a read-only token; only the jobs that run no pull request code may comment. The release cut's own token may dispatch a workflow in this repository (GitHub lets a `GITHUB_TOKEN` start `workflow_dispatch` runs), which is how it starts the release run. Comments, the status and the issue are written with the run's own `GITHUB_TOKEN`.

## Should we adopt `async/pipeline`?

[`async/pipeline`](https://github.com/async/pipeline) writes the task graph once in a `pipeline.ts`, runs it locally, and generates a thin GitHub Actions workflow that calls the same graph. That is the right idea: one source for local and CI commands. The recommendation is **not now**:

- **It does not address the main causes.** The history is dominated by commands that were never run before pushing, by red left red, and by Linux-only differences. A shared task graph run on the Mac still runs on macOS with the Mac's browsers and untracked files. The rules above and `ci:local --clean`/`--linux` target those causes directly.
- **The single-source goal is already met without a migration.** `ci:local` derives its commands from `ci.yml` in one 480-line script with no new dependency. Adopting `async/pipeline` means rewriting a 1,261-line workflow, including content-hash lane skipping, sharding, artifact hand-off between box lanes and `receipts`, Playwright caching, and the benchmark baseline worktree. Each of those is a place to introduce a new failure.
- **Maturity.** Created 2026-06-04, 3 stars, last push 2026-07-08, requires Deno 2 alongside Node 24. The repository already uses `@async/witness` from the same organisation, so the maintainers are reachable, which lowers the risk, but a 0.9 tool on the merge gate is still a dependency on its release cadence.

Revisit if the workflow grows another layer of CI-only logic that `ci:local` cannot read from the YAML (for example, job graphs whose commands are computed at run time), or if `async/pipeline` gains a container runner that would replace `--linux`.
