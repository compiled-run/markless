## Ranking
1. QT — Every feature is gated by its own `.supported` check and has a clear fallback. `modifierKey === '⌘'` says outright that it's about the user's keyboard, so a Mac visitor on the website gets ⌘K. You can read off what the website and the iPhone each get, assuming `.supported` means "works here".
2. VR — `platform.ios || platform.android` names exactly who gets each feature, so iPhone versus website is easy to read. But it says nothing about the Mac app, which gets no camera, location, Share or offline banner, maybe by accident. `platform.macos` in the search hint has the same ambiguity as GP. It also hard-codes the platform list instead of asking what actually works.
3. GP — The same structure as QT, but `platform.macos` could mean the Mac app or a Mac computer, so the search hint for a Mac browser is a guess. This is the version I answered first.
4. LX — Support is found by catching errors: `@try`/`@catch` around each piece and `try`/`catch` around haptics and share. You only get the fallback text if something throws, and the code doesn't say whether it throws when the feature is created, when it's used, or never. Each piece is its own small component, which reads fine, but you can't tell up front what the website shows.
5. HN — Nothing is gated. You can't tell from the code whether the website shows a camera view that never works, a Take photo button that's disabled forever, "Finding you…" forever, or a Share button that does nothing. Possibly the library handles all of this, but the code gives no hint.

B: Most trusted: QT. Each button appears only when its own `.supported` check passes, and none of its buttons depend on the ambiguous `platform` flags. A close second is LX's Share, which shows "Sharing works in the app." when sharing fails, but only if `open` actually throws. Least trusted: HN. Share and Take photo always render, with no check and no fallback, so on the website they could easily do nothing. Like's haptics also do nothing on the web in every version, though the count still goes up.

C: Two answers shifted a little; the rest stand.

1f: Seeing `modifierKey` used elsewhere makes it more likely that `platform.macos` means the Mac app build. That would mean a Mac browser visitor sees "Ctrl+K". I now lean that way instead of treating it as 50/50.

1c and question 3: LX wraps `haptics.tap` in `try`/`catch`, which suggests it might throw on the web. In GP the count would still go up because `likes++` runs first, but there could be an uncaught error.

VR's hard-coded platform checks also strengthen my reading that GP's `.supported` checks are about what actually works on the device. So a Mac browser might get the Share button, and network status is probably supported on the web. My confidence for question 1 stays at 2.
