## Ranking
1. VR: Each feature is gated on `platform.ios || platform.android`, so you can read exactly what the website and the iPhone get: the website gets the "works in the app" text, and the iPhone gets the camera, location and Share. The cost is that it hard-codes platforms. The Mac app is told the camera "works in the app" even though it is the app, and the website never shows the offline banner.
2. GP: The `.supported` checks with visible fallback text, plus an explicit `platform.macos`, make both outcomes readable. You still have to guess what `.supported` returns on the website, though the fallback wording strongly suggests false.
3. QT: Same structure as GP, but the hint uses `modifierKey === '⌘'`, which leaves the per-platform value of the search hint a guess.
4. LX: The `@catch` fallbacks show that the website may fail, but only at runtime and only by inference. You can't tell from the code whether the camera preview renders and then breaks, or whether the fallback text shows straight away. The `try {}` around haptics hints that it might throw.
5. HN: Nothing in the code marks the difference between platforms. Every website outcome is a guess.

B: I would trust GP most, with QT a close second. Share only appears when `sharesheet.supported` is true, and the camera and location have explicit fallbacks. VR also hides Share on the website, but only through a hard-coded platform list. I would trust HN least. Share is always rendered with no check or catch, so it could do nothing (or throw silently) on the website. The camera, location and offline banner could also show states that never resolve.

C: Yes. The other versions all imply that the website build may not support the camera, location, share sheet or network status, since they show "works in the app" or hide those pieces. So my question 1 answers for HN assumed too much:

- **1a (camera):** HN may show an empty or broken preview with "Take photo" disabled forever, rather than a working webcam.
- **1b (location):** the page may sit on "Finding you…" forever.
- **1d (offline banner):** QT and GP gate it on `network.supported`, so in HN `net.online` may never change on the website and the banner may never appear.
- **1e (Share):** LX catches an error from `sharesheet.open`, so in HN Share probably throws silently and does nothing on the website. That makes my question 3 answer firmer.
- **1c (Like):** LX's `try` around haptics suggests `haptics.tap` might throw on the website. The count would still go up first.
- **1f (search hint):** VR and GP switch on `platform.macos`, which supports my reading that '⌘' means macOS. The iPhone probably shows "Ctrl+K", as I guessed.

My confidence in question 1 drops from 3 to 2.
