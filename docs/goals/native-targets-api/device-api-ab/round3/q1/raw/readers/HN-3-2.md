## Ranking
1. VR — Every device feature sits behind an explicit `platform.ios || platform.android` check, so you can read straight off the code that iPhone gets camera, location, the offline banner and Share, while the website gets "works in the app" text and no Share button. One thing stays unclear: whether a browser on a Mac counts as `platform.macos`. It also oddly treats the Mac app like the website.
2. GP — Each feature is gated by its own `.supported` flag, with visible fallback text, and `platform.macos` makes the search hint plain. You still have to guess which flags are true on the website, though the "works in the app" fallbacks strongly hint that they are false there.
3. QT — Same structure as GP, so equally honest about the gating. It ranks lower only because `modifierKey` is less obvious than `platform.macos`.
4. LX — The fallbacks exist, but they only appear when something throws, inside `@try`/`@catch` and `try {}`. You learn what the website gets only by guessing what throws. Share always shows a button, and the "works in the app" note appears only after pressing it.
5. HN — There are no signals at all. Nothing tells you whether the camera, location, network or share sheet work on the website, do nothing silently, or throw.

B: I'd trust GP most, with QT tied in practice: Share is only shown when `sharesheet.supported` is true, and the camera button is replaced when there is no camera. VR is also safe for the website, but only because it hard-codes which platforms get the feature. I'd trust HN least, since its Share button (and possibly the camera and location sections) could ship dead on the website with nothing in the code to say so. LX doesn't leave Share dead, but it does show a Share button that only explains itself after being pressed. In every version, Like's haptic tap does nothing on the web, but the counter still works, so the button isn't dead.

C: Yes, it changed several answers:
- **1a, 1b, 1e:** I had assumed the website uses the browser's camera, location and web sharing. Four of the five versions show "works in the app" or hide the feature on the website, which suggests the package may not support them on the web at all. If so, HN on the website might show an empty or never-ready camera with Take photo disabled forever, sit on "Finding you…" for good, and have a Share button that does nothing or throws an error. LX suggests these calls may throw when unsupported.
- **1d:** `network.supported` (QT, GP) and VR's mobile-only gating suggest offline detection may not work on the website. The banner might never appear there.
- **1f:** `platform.macos` standing in for `modifierKey === '⌘'` confirms that `modifierKey` means "the platform's modifier key", so ⌘K on a Mac. Whether iPhone counts as ⌘ is still a guess.
- **3:** Share on the website is now my main candidate for a button that does nothing, possibly along with a Take photo button that never becomes enabled.
- **4:** VR, QT and GP show that platform differences could be written into the page itself. HN writes none, so everything is left to the package, which is unknown.
- **5:** My confidence drops from 3 to 2.
