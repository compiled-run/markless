## Ranking
1. VR — It names platforms directly (`platform.ios || platform.android`), so you can read off what each build shows. The website gets the fallback text, no Share button and no offline banner; the iPhone gets everything. The only open question is whether `platform.macos` means the Mac app or any Mac, including a Mac browser.
2. GP — `.supported` checks make every fallback visible beside the feature, and `platform.macos` makes the search hint clear. But you still have to guess whether `camera.supported` or `sharesheet.supported` is true in a browser, so the website outcome isn't fully readable.
3. QT — The same as GP, but `modifierKey === '⌘'` is less clear than `platform.macos` about which systems count as Mac.
4. LX — Unsupported features can only be inferred from `@try`/`@catch` and the messages inside them. The catches also swallow real failures such as a denied permission or a cancelled share, and show "works in the app" even inside the app. You can't tell from the code which platforms throw.
5. HN — Nothing in it signals platform differences. The website outcome of every device call is pure guesswork: it might throw, do nothing, or work through the browser.

B: I would trust GP or QT most, because Share only renders when `sharesheet.supported` is true. VR is nearly as safe, but it hides Share on the web even where the browser could share. I would trust HN least, because Share is always rendered and unguarded, so on the website it may do nothing or fail silently. In every version except LX, Like's `haptics.tap` is also unguarded. The counter still goes up, so the button is not dead, but the haptic part does nothing on the web.

C: Yes, in three ways:
- The other designs show that the device package can offer `.supported` and `platform`, so in LX's design `@try`/`@catch` looks like the only way to detect support. That makes me more confident in 1a and 1b: the website most likely shows "The camera works in the app." and "Location works in the app."
- VR shows the offline banner only on iOS and Android, which suggests `network()` may not be supported on the web. That makes me less confident in 1d: the banner might never appear on the website because the empty catch renders nothing.
- GP and VR use `platform.macos` where LX uses `modifierKey === '⌘'`, which supports my 1f answer that a Mac browser shows ⌘K. 2f is still uncertain.

I also see more clearly that LX's catches mislabel in-app failures, such as a denied permission or a cancelled share, as "works in the app".
