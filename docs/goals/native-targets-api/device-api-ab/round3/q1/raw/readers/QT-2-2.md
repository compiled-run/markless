## Ranking
1. VR: every gate is named by platform (`platform.ios || platform.android`, `platform.macos`), so you can read straight off the code that the website gets the "works in the app" fallbacks and the iPhone gets the camera, location, offline banner and Share. Its weakness is that it hard-codes which platforms qualify, so a Mac app or a capable browser is left out by decision rather than by what the device can do.
2. GP: the `.supported` gates mark each feature as possibly missing, and the fallback text hints that the website lacks them. `platform.macos` makes the search hint unambiguous. You still have to guess what `.supported` returns on the web.
3. QT: the same as GP, but `modifierKey === '⌘'` adds one more unknown, since it doesn't say what it returns on a phone or in a browser.
4. LX: what a visitor gets depends on runtime errors caught by `@try`/`@catch`. You can only infer that something throws on the web, not what throws or when. Share is always shown and only after a press do you learn it doesn't work.
5. HN: there are no gates or fallbacks at all. Nothing in the code tells you what happens on the website; everything depends on undocumented package behaviour.

B: Most trusted is VR. Share appears only on iOS and Android, so the website can never show a dead Share button; the only call it leaves unguarded is haptics, which is a side effect of a button that still counts. GP and QT come close, if `.supported` is accurate. Least trusted is HN. It always renders Share and Take photo with no check, so on the website Share may silently do nothing or throw an error. LX also shows Share on the website, but at least it shows "Sharing works in the app." when pressed.

C: Yes, in two ways.
- **More certain (1a, 1b, 1d, 1e):** VR puts `platform.ios || platform.android` exactly where the first version (QT) has `.supported`, with the same fallback text. That makes me more confident the `.supported` flags are false on the website. So in 1a and 1b the visitor most likely sees "The camera works in the app." and "Location works in the app.", in 1d there is probably no offline banner, and in 1e there is probably no Share button. I had leaned toward "browsers can do this" before. This is still inference, not certainty.
- **Less sure (1c, 3):** LX wraps `haptics.tap` in try/catch, which suggests it may throw where haptics isn't supported, not quietly do nothing. If so, on the website in QT a click on Like still adds 1 first, then possibly throws an error. My answers to 1c and 3 are less certain than I said.

1f is unchanged: `platform.macos` in VR and GP suggests `modifierKey` is '⌘' on a Mac.
