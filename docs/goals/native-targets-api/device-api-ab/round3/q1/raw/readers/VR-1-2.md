## Ranking
1. VR — Every split is one plain rule, `platform.ios || platform.android`, with an explicit `@else` for everyone else. You can read off what the website and iPhone each get without knowing anything about the package. The one unclear point is whether `platform.macos` means the Mac app or a Mac running a browser.
2. QT — Each feature has its own `.supported` check plus a fallback text. `modifierKey` settles the ⌘/Ctrl question for a Mac browser. But you have to guess which features count as "supported" on the web, since browsers do have location and sometimes sharing.
3. GP — It has the same `.supported` checks as QT, but goes back to `platform.macos` for the search hint, so the Mac-browser question comes back. It mixes two ways of asking.
4. LX — The fallbacks are written down, but you only learn what the website gets if a feature throws an error. Whether `camera()` or `sharesheet.open` fails on the web, and when, is hidden in runtime behaviour. The `try {} catch {}` around haptics hides failures.
5. HN — Nothing is checked, so the code cannot tell you what a website visitor gets compared with an iPhone user. Everything is rendered for everyone.

B: Most trusted is QT. The Share button only renders when `sharesheet.supported` is true, and GP does the same. VR is close behind, but it uses the platform as a stand-in for the capability, which could be wrong in either direction. Least trusted is HN: Share, Take photo and the haptic are shown to everyone, with no hint of what happens on the web. LX is next to last, but its Share button at least shows "Sharing works in the app." instead of doing nothing.

C: None of my answers to the first version (VR) actually changed. Two of them got firmer:
- 1f: The other versions use `modifierKey` for the visitor's own keyboard. That supports my reading that `platform.macos` means the Mac app build, so a Mac browser probably sees "Ctrl+K", which is the wrong hint for that user.
- 3 and 4: The `.supported` versions suggest that location and sharing may well work on the web. So in VR, hiding location and Share on the website and the Mac app is the page author's choice, not a limit of the platform. This also suggests VR's checks run when the page runs rather than being removed at build time, but that is still a guess.
