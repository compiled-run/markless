## Ranking
1. VR — It names the builds directly (`platform.ios || platform.android`), so you can read straight off the code which pieces each build gets. Its weak spots are that `platform.macos` could mean the Mac app or any Mac, and that tying features to an operating system rather than to the feature means the Mac app gets no camera or location even if it could.
2. QT — Each feature is checked by its own `.supported`, and `modifierKey` says plainly what the hint wants. However, you have to know which builds support each feature. A browser can often use a camera and location, so the "works in the app" fallback text is the only clue that the website reports these as unsupported.
3. GP — The same as QT, but the search hint uses `platform.macos`, which brings back the "Mac app or any Mac?" question.
4. LX — The "works in the app" fallbacks are written out. But whether a visitor sees them depends on whether `camera()` or `geolocation()` throws at runtime, which the code does not show. On the website, Share is a working button that only shows a note when pressed.
5. HN — There are no checks at all. Every piece renders in every build, and the code gives no hint of what happens on the website: no camera, a stuck "Finding you…", or a Share button that does nothing.

B: I would trust QT most, with GP close behind. Share appears only where `sharesheet.supported` is true, and the check comes from the feature itself, not from a list of platforms that could fall out of date. VR also hides Share on the website, but it hard-codes the platform list. I would trust HN least: it always renders Share and Take photo with no check, so on the website they may do nothing. LX is next to last: its button does something, but only after the visitor presses it and gets "Sharing works in the app."

C: Yes, two changes.

The page might fail to load on the website: LX wraps each `camera()`, `geolocation()` and `network()` call in its own component inside `@try`, which suggests these calls may throw where the feature is unsupported. VR calls all three at the top of the page with no check. If they throw on the website, the whole page might fail rather than showing the "works in the app" texts. QT and GP make the same top-level calls and look designed to be safe, so that is still my main reading, but I am less sure now.

The search hint (1f) is less certain than I said: The `modifierKey` versions suggest the hint is really about the visitor's keyboard. So for a Mac laptop visitor, VR's `platform.macos` may wrongly show "Ctrl+K" if it means the Mac app build. This makes me less sure of my "Ctrl+K" answer.

My confidence in question 1 drops from 3 to about 2.5 out of 5.
