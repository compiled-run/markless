## Ranking
1. IA — It answers all three questions in the code itself. Each target gets its own tag (`ios.camera`, `android.camera`, `web.camera`), so you can see where each comes from, that each platform draws its own, and exactly what the website gets. The cost is length: the sheet and its contents are written three times, so "Choose a filter" appears in three places.
2. SY — `system.sheet` and `system.camera` say outright that the system draws them, and they come plainly from `@markless/ui`. What the website gets is still implied rather than shown, but "system" carries over naturally to "the browser's version".
3. NT — `native` strongly suggests the OS draws it. On the website, though, "native" reads as "not available here" or "the app only", so a reader could easily think the website gets nothing.
4. PF — `platform` is imported from `@markless/device`, not `@markless/ui`, so the tags seem to come from the device package. That blurs where they come from. The same object also answers "which platform is this?" (`platform.ios`), which mixes a component namespace with a runtime check. What the website gets is unclear.
5. BC — `base` sits right beside `base.button`, which looks like a plain building block the author styles. So `base.sheet` and `base.camera` read as page-drawn, not system-drawn. Nothing hints at what the website gets.
6. BT — Bare `<camera>` and `<sheet>` have no import, so they look like HTML or unknown custom elements. You can't tell where they come from, who draws them, or what the website gets.

B: `system`. It names who draws the thing (the operating system, or the browser on the website), and it stays true on every target. `native` comes close, but it suggests "not the website". `platform` is already taken by the "which platform am I on?" check. `base` suggests an unstyled starting point the author builds on. The per-platform names `ios`/`android`/`web` are the most explicit, but they push branching and duplication onto every page. A bare tag tells the reader nothing.

C: It could be confused. `platform.ios` is a true/false check and `platform.sheet` is a component, yet they look the same, so a reader might take `platform.ios` for a component or `platform.sheet` for a flag. It also raises questions like "is there a `platform.web` component?" and "does `platform.sheet` only exist on some platforms?". Putting the components in `@markless/device` rather than `@markless/ui` adds to the muddle.

D: SY. I'd write one tag that works on every target, and its name tells the next reader the system draws it, with no branching and no duplicated content. When I truly need a different look per platform, I'd use IA-style per-platform tags at that one spot.

E: Yes, on three answers. For Q3, seeing `base.button` and `base.sheet` side by side in BC makes `base` read as "plain building block", which weakens my guess that the system draws the `base.sheet`. For Q2, IA's `web.camera` and `web.sheet` suggest both really do have a website version, so my "probably exists on the website" stands a little firmer. For Q6, IA sends `platform.ios` to `ios.camera` and everything else to `web.camera`. That only makes sense if `platform.ios` is true in the iPhone app and not in Safari on an iPhone, so I'm more confident the note shows only in the iPhone app. My confidence on Q6 goes from 2 to 3. Q2 stays about 2, rising to 3 only if IA reflects the real design.

Tools used: none
