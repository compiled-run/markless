## Ranking
1. IA: The only version that shows what the website gets. `web.camera` and `web.sheet` sit in an explicit `@else` branch, and `ios.*`/`android.*` make it clear the platform draws them. The cost is that the sheet is written three times and the logic is spread across branches.
2. NT: `native.camera` and `native.sheet` say "drawn by the platform" with the most widely known word, and both clearly come from `@markless/ui`. It does not say what a browser gets, though. "Native" on the web is ambiguous: a browser fallback, or nothing at all?
3. SY: `system` says "the host draws this" almost as well as `native`, and it stretches more naturally to the web, where the browser counts as the system. The word is less common, and it could also be read as "a design-system component".
4. PF: The intent is clear ("the platform's camera/sheet"), but the tags come from `platform`, which is imported from `@markless/device`, not from the UI package. So the components' source is surprising, and the same object is both a flag and a source of tags (see C).
5. BC: `base` reads as "default/unstyled primitive", the same family as `base.button`, which is plainly not a platform-drawn control. Nothing signals that the system draws the camera or sheet, or what the web gets. I only guessed it in my first answers.
6. BT: A bare `<camera>` or `<sheet>` looks like an HTML element or a built-in Markless tag. `<camera>` also collides with the imported `camera()` function from `@markless/device`. The source, who draws it, and the web behaviour are all invisible.

B: `native`. It is the established term for "the platform's own control, not drawn by the page", and readers coming from React Native, Flutter or SwiftUI already read it that way. `system` is a close second and covers the browser case a little better. Per-platform `ios`/`android`/`web` is the most explicit, but it makes the author branch and duplicate code, so it names the platforms rather than the idea. `platform` collides with the platform flags. `base` suggests "unstyled starting point", which is closer to the opposite meaning. A bare tag says nothing.

C: The two uses can be confused. `platform.ios` is a yes/no answer to "which platform am I on?", while `platform.sheet` is a component. Seeing them side by side, a reader could take `platform.sheet` as a flag ("does this platform have a sheet?"). Or they could take `platform.ios` as an iOS-only namespace like `ios.*` in IA, and then look for `platform.ios.sheet`. It also places UI components in `@markless/device` instead of `@markless/ui`, which blurs the line between the two packages.

D: NT. It is one tag per feature with no branching, the name says the platform draws it, and the sheet is written once. I would want the documentation, or a type hover, to state the web fallback. If the web behaviour needed to be visible at the call site, IA makes it so, but at the cost of tripling the sheet. I'd only reach for it when the platforms really do need different content.

E: Yes, the first version was BC, and several answers changed:

Q3: I read `base` as "the platform's own control", but that was a guess. Next to `native`/`system`, and next to `base.button` (clearly a page-styled toggle), `base` more likely means "default primitive". I'm now less sure the system draws the base sheet and camera at all; the drawer and the sheet may differ mainly in single tag vs. assembled parts, not in who draws them.

Q2: IA suggests that the web gets its own `web.camera`/`web.sheet` versions rather than nothing. That supports my guess of a browser fallback, as long as all six versions share the same meaning.

Q6: In IA, `platform.ios` picks `ios.camera`, and everything else falls to `web.*`. That implies `platform.ios` means "the iPhone app build", not "any iPhone", so Safari on an iPhone would get the web branch and not see the note. This makes my "iPhone app only" guess stronger, but it is still a guess.

Q5: This stays one place in BC. In IA it would be three.
