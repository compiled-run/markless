## Ranking
1. NT: `native.camera` and `native.sheet` say plainly that the platform draws them, and `base` stays for the ordinary components. The website result is still a guess, probably a web stand-in.
2. IA: this is the only version that shows what the website gets: `web.camera` and `web.sheet` in the `@else` branch. It is ranked below NT because it repeats the sheet three times and still doesn't say whether `web.sheet` is drawn by the browser or by the library.
3. SY: `system.camera` and `system.sheet` also read as "drawn by the platform". `system` is a little vaguer than `native`, because it could mean the operating system or the framework's own design system.
4. PF: here `platform` is imported from `@markless/device`, so the sheet seems to come from the device package, not the UI one. That clashes with `@markless/ui`. It also shares a name with the `platform.ios` check (see C).
5. BC: `base` sounds like "plain building blocks", not "drawn by the platform". It is also the namespace of `base.button`, which doesn't look system-drawn, so the camera and sheet don't stand out from it.
6. BT: `<camera>` and `<sheet>` are not imported, so they look like HTML or tags built into Markless. Nothing tells you where they come from, who draws them, or what the website gets.

B: `native`, because it is the common word for "the operating system's own control, not one the page draws". Per-platform `ios`/`android`/`web` is the most explicit, but each name covers only one platform. `system` is a close second. `platform` clashes with the `platform.ios` check. `base` suggests building blocks, and a bare tag tells you nothing.

C: It could be confused. `platform.ios` is a yes/no fact about where the app runs, while `platform.sheet` is a component. A reader could take `platform.sheet` for a flag ("does this platform have sheets?"), or guess that it belongs to whichever platform `platform.ios` reports, or that it only exists on some platforms. Importing a component from `@markless/device` instead of `@markless/ui` adds more doubt about where it comes from.

D: NT. It is one tag per feature with a clear meaning, and the website fallback is left to the library. IA is clearer about the website, but every change to the sheet's contents has to be made three times, as the next answer shows.

E: Yes, three answers. The first version was BC.

Question 3: seeing `native` and `system` as alternatives, and seeing `base.button` share the `base` namespace, makes my guess that `base` means "system-drawn" weaker. Before, I read it as system-drawn; now I think `base` may just mean basic building blocks.

Question 6: IA uses `platform.ios` to choose `ios.camera`, with `web.camera` in the `@else`. That only works if `platform.ios` means the iPhone app build, not Safari on an iPhone. So my answer that only the iPhone app user sees the note is now better supported.

Question 5: for BC the answer is still one place. In IA the heading would need three changes, one in each sheet branch.
