## Ranking
1. IA — It shows the most of any version. Separate `ios.`, `android.` and `web.` branches spell out what each target gets, including the website (`web.camera`, `web.sheet`). The imports show the tags come from `@markless/ui`. It also implies that `platform.ios` means the iPhone app. The cost is real: the sheet body is written three times, and so is the heading "Choose a filter".
2. SY — The `system.` prefix says "drawn by the operating system" most directly, and the import shows where it comes from. "System" also reads naturally on the website, where it would mean the browser's own control. It doesn't say what the website gets, but the word doesn't contradict a web build.
3. NT — `native.` clearly means "the platform draws this, not the page", and the import shows where it comes from. But "native" in a website build is confusing: does a browser visitor get it at all, or a fallback?
4. PF — It says "platform-drawn", but `platform` is imported from `@markless/device`, so the sheet seems to come from a device package rather than the UI package. The same object also answers `platform.ios`, which is a yes/no question, not a component.
5. BC — It is actively misleading. `base.button` on the same page is an author-styled headless part, so `base.sheet` reads as another unstyled piece the author must style. Nothing suggests the system draws it.
6. BT — There is no import, so the reader can't tell where `<camera>` and `<sheet>` come from. They look like HTML elements that don't exist, and nothing says who draws them or what the website gets.

B: `system` is the best name. It names who draws the control (the operating system or the browser) and stays true on every target, the website included. `native` says the same thing on the phones but sounds wrong for a website build. `platform` is overloaded, because it is already the object you ask "which platform am I on?". `base` already means "headless, you style it" on this page. Separate `ios`, `android` and `web` names are precise, but they push the reader to branch and duplicate code. A bare tag says nothing.

C: The two uses can be confused. `platform.ios` is a yes/no value, while `platform.sheet` is a component, and both hang off one object from `@markless/device`. A reader might take `platform.sheet` to mean "the sheet only on some platforms". Or they might reach for `platform.ios.sheet`, or wonder whether `platform.sheet` changes depending on `platform.ios`. Mixing "which platform is this?" with "a control drawn by the platform" on one object makes it hard to tell the two roles apart.

D: I would rather write SY. It is one tag per control with one copy of the content, a clear import from `@markless/ui`, and a name that says the system draws it. NT is a close second. IA is clearest to read, but triplicating the sheet makes edits error-prone; changing the heading would mean three edits.

E: Yes, the other versions changed several answers.

- **Question 1**: I had guessed the bare `<camera>` came from `@markless/device` because of the matching `camera` import. Every other version imports the drawn controls from `@markless/ui`, even PF, whose namespace is the device package's `platform` object. So the bare tags are more likely Markless built-ins or `@markless/ui` controls exposed without a prefix. I'm now less sure of my device-package guess, and BT's origin is simply unknowable from its own code.
- **Question 6**: IA strengthens my reading that `platform.ios` means the native iPhone app. Its `@else` branch gives the website `web.camera`, so an iPhone Safari visitor must be landing in the `@else` branch, because a browser can't run `ios.camera`. That backs my answer that only the app user sees the library note. My confidence goes from about 2 to about 3 out of 5.
- **Question 2**: IA's `web.camera` and `web.sheet` support my guess that the website gets a web version of both controls rather than nothing.
- **Question 3**: unchanged. BC made me notice that `base` could be read both ways, but `base.button` is still most plausibly author-styled.
