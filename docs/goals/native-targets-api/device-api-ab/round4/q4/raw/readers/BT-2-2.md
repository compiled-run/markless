## Ranking
1. NT — `native.camera` and `native.sheet` show that the platform draws these two, the import shows they come from `@markless/ui`, and the `drawer` parts next to them are clearly the page-styled kind. It does not say what the website gets, though I would guess an equivalent made for the web.
2. SY — This works the same way as NT and is almost as clear. "System" does suggest the operating system draws it, but it is a little vaguer: it could mean "system defaults" or "design-system component" instead of native UI.
3. IA — This is the most explicit about what the website gets, because there is a literal `web.camera` and `web.sheet` branch, and it is obvious the platform draws each one. It costs a lot, though. The sheet body appears three times, so changing the heading means three edits, and the reader has to check that the three copies match. Clear but noisy.
4. PF — It says the platform draws them, but `platform` is also the object you query with `platform.ios`. So `platform.sheet` could read as "the sheet only on platforms that have one" or as a property lookup, not a tag. It also comes from `@markless/device`, which mixes device features with UI.
5. BT — Neither tag is imported, so where they come from is a guess. `<camera>` clashes with the imported `camera()` function, nothing says the system draws them, and nothing says what the website gets. This is the version I first answered from, and I had to guess almost everything.
6. BC — This is actively misleading. The page uses `base.button` as a component it styles itself, so `base.sheet` and `base.camera` read as the same kind: unstyled parts the author styles. That is the opposite of "drawn by the system".

B: `native` is best. In app-developer vocabulary it already means "the platform's own UI control, not one drawn by the page", and it is a single name that holds for every build, including the website, where it would mean the browser's own element. `system` comes second but is vaguer. Per-platform `ios`/`android`/`web` is very precise but forces branching and copies of the same content. `platform` gets mixed up with the platform-detection object. `base` already means "unstyled part the page styles" because of `base.button`. A bare tag says nothing about where it comes from.

C: It could be confused. `platform.ios` is a true/false check, while `platform.sheet` is a component, so one object holds both answers to "which platform is this?" and the things that platform draws. A reader may think `platform.sheet` is only defined on some platforms, much like `platform.ios` is only true on some. They may also wonder whether `platform.camera` is a fact about the device, like "has a camera". It also puts UI tags in `@markless/device`, next to `camera()`, the controller, which makes `<platform.camera>` versus `camera()` another pair of near-identical names.

D: I would rather write NT. It is one line per control, and the import tells the reader both where the tag comes from and who draws it. It needs no branching or copies, so the heading changes in one place. It also sits cleanly beside `base.*` and `drawer.*`: native means the system draws it, and the others mean the page styles them. If I needed to change behaviour per platform, I would still prefer one `native.sheet` and only branch with `@if (platform.ios)` where behaviour actually differs. IA's three-way copying gets out of sync easily.

E: Yes, the first version I answered from was BT, and three answers changed:

Q1 (where the tags come from): NT, SY and BC all import these tags from `@markless/ui`. That makes me think they come from a package, not from Markless itself, so my BT answer of "built into Markless" may be wrong. It also suggests the bare `<camera>` was not meant to be the `camera()` function from `@markless/device`.

Q2 (what the website gets): IA's `web.sheet` and `web.camera` support my guess that the website gets its own web version, not nothing or an error. My confidence goes from 2 to about 3 out of 5.

Q6 (who sees the note): IA uses `platform.ios` to choose between `ios.sheet` and `web.sheet`. An iPhone Safari visitor can only sensibly get the web sheet, so `platform.ios` most likely means the iPhone app build, not the visitor's operating system. That supports my answer that only iPhone app users see the note. My confidence goes from 2.5 to about 3.5 out of 5.

My answers to Q3–Q5 did not change for BT, but under IA the heading would need three edits, not one.
