## Ranking
1. NT — `native.camera` and `native.sheet` come visibly from `@markless/ui` under a name that says "drawn by the platform". You still have to guess what the website gets, but the name suggests a native view with a web fallback.
2. IA — the clearest on what the website gets (`web.camera`, `web.sheet`), and the source of each tag is plain. But it says it three times, so the sheet contents appear three times and could drift apart. It also implies each platform needs separate code, which may not be true.
3. SY — the import is clear, and `system` hints that the operating system draws it. But "system" could also be read as "design system", meaning the app's own component library.
4. PF — puts the components on `platform` from `@markless/device`, so a sheet now comes from the device-features package. The name hints at "platform-drawn", but it shares an object with the `platform.ios` check (see C).
5. BT — bare tags: no import, no clue whether they are HTML, Markless built-ins or tied to the `camera` binding. Unclear, though at least it doesn't point you the wrong way.
6. BC — actively misleading. `base.button` on the same page is a component the author styles, so `base.sheet` reads as the same kind of thing, not as something the system draws.

B: `native`. It is the established word for "the operating system's own view, not something the page draws", it is short, and it says nothing false about the website, where "a native fallback" is easy to accept. `system` comes second but is ambiguous. `platform` already names the "which platform am I on" check. `base` already means "unstyled, author-styled". The per-platform names say too much and force three branches. A bare tag says nothing at all.

C: They can be confused. `platform.ios` is a yes/no question about where the code is running, while `platform.sheet` is a component, so one object mixes questions and things to render. A reader could take `platform.sheet` to be iOS-only, or think of it as data rather than a tag. It also sits beside `camera()` from the same package, so there are two different "camera" things from `@markless/device`. Finally, putting UI components in the device-features package blurs which package owns what.

D: NT. It is one line per element and the name is honest. The sheet contents are written once (IA repeats them three times), it doesn't clash with `base` or `platform`, and the import shows where the tags come from. I'd only want the docs to say what each `native.*` tag renders on the website.

E: Yes. The first page I read was BT. Question 6: IA's three-way `platform.ios` / `platform.android` / else-`web` switch strongly suggests that `platform.ios` means "running as the iPhone app" and that the website, including Safari on an iPhone, takes the `web` branch. So the note shows only in the iPhone app, and my confidence goes from 3 to 4. Question 2: `web.camera` and `web.sheet` in IA suggest the website gets real web versions of both rather than having them dropped, which backs up my guess (confidence from 2 to 3). Question 1: the other versions suggest the bare tags are Markless or `@markless/ui` native components rather than tags tied to the `camera` import. That is still a guess for BT itself. Question 5: unchanged for BT (one place), but in IA it would be three.
