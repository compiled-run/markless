## Ranking
1. IA — The source is explicit: the `ios`/`android`/`web` namespaces are imported from `@markless/ui`. The `web.*` branch shows exactly what the website gets, and per-platform names strongly suggest the platform draws each one. The cost is three copies of the sheet's content and a branch at every use.
2. SY — `system.camera` and `system.sheet` are imported from `@markless/ui`, and "system" says outright that the OS draws it, not the page. A browser can be the "system" too, so I guess the website gets the browser's own version. The tag doesn't say so, though.
3. NT — The source is clear and "native" strongly says the platform draws it. On the website, "native" is confusing: the reader can't tell whether the tag renders, falls back, or is missing.
4. PF — It reads as "the current platform's camera", which hints that it differs per platform. But the tag comes from `@markless/device` (the `platform` object), not from `@markless/ui` where the other components live. `platform.sheet` also sits right next to the boolean `platform.ios`, and the website result isn't stated.
5. BC — Misleading. The same file uses `base.button`, which most readily reads as a plain building block that the page styles. Putting `camera` and `sheet` under `base` suggests the page draws them too, which is the opposite of what is meant.
6. BT — A bare `<camera>` or `<sheet>` looks like an HTML element or a Markless built-in, and nothing is imported for it. Worse, `camera` is also the function imported from `@markless/device`, so the reader can't tell whether `<camera>` is that function or a separate tag. Nothing says who draws it or what the website gets.

B: `system` is best. It names who draws the thing (the operating system, or the browser on the web) and still makes sense on all three targets. `native` comes close, but it implies "not the web", so it is wrong on the website. Per-platform `ios`/`android`/`web` is clear but tells you which platform, not who draws it, and forces branching. `platform` collides with the `platform.ios` checks. `base` reads as "plain, the page styles it", the opposite meaning. A bare tag says nothing and looks like HTML.

C: It could be confused. `platform.ios` is a yes/no fact about where the code runs; `platform.sheet` is a component. Seen together, a reader could think `platform.sheet` is also a check ("is there a sheet?"), or that `platform.ios` is a component. Because both sit on one object, a reader might also try `<platform.ios.sheet>`. It also moves a UI component into `@markless/device`, which blurs which package owns components and which owns device facts.

D: I would rather write SY. It is one tag with no branches and no copied content, so changing "Choose a filter" means one edit instead of three, and the name keeps saying that the system draws it. If I needed different content on one platform, I would still want IA-style namespaces available as an escape hatch.

E: Mostly no, with two small adjustments.
- Question 2: the single-tag versions imply one component has a web form. That supports my guess that `web.camera` and `web.sheet` in IA give a real browser camera preview and a web sheet, not just a placeholder. It doesn't confirm it.
- Questions 1 and 3: BC made me less sure that `base` means "unstyled, the page styles it". If `base.camera` were a real system-drawn component, then `base` could just mean "common", and `base.button` might have a default look.

Question 6 is unchanged. Every version keeps `@if (platform.ios)` for the note, so the meaning of `platform.ios` is still the open question. I still guess that only iPhone app users see the note.
