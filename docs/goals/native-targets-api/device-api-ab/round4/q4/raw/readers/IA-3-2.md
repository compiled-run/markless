## Ranking
1. IA — Clearest of the six, though the most verbose. Every branch names its source (`@markless/ui`'s `ios`, `android` and `web`), and the `@else` with `web.camera` and `web.sheet` shows exactly what the website gets. What is still hidden is whether `platform.ios` means the app build or the device's operating system.
2. PF — `platform.camera` reads as "this platform's camera". It comes from `@markless/device`, which already provides `camera()`, so it is clear the platform supplies and draws it. You can infer the website gets the web platform's version. The cost is that it shares a name with the `platform.ios` flag.
3. SY — `system.sheet` clearly says the operating system or browser draws it, and "system" still fits on the web. It does not say what the website gets, and it does not show that it changes per platform.
4. NT — `native` says most strongly that the platform draws it, not the page. But on the website it suggests either nothing (no native layer) or something native-only, so what the website gets is the least clear of the named options.
5. BC — Misleading. `base.button` on the same page looks like an unstyled, author-styled part, so `base.camera` and `base.sheet` read as "plain building block styled by the page". That is the opposite of system-drawn.
6. BT — A bare `<camera>` or `<sheet>` with no import looks like an HTML tag, a custom element or a Markless built-in. Nothing tells you where it comes from, who draws it, or what the website gets.

B: `system`. It says "drawn by the OS or browser, not by the page" without promising a native layer the website doesn't have, and it doesn't clash with the `platform.ios` flags. `native` carries the meaning most strongly but suggests the tag doesn't exist on the web. `platform` works but overlaps with the flag. Per-platform `ios`/`android`/`web` is the most explicit but makes you write the code three times. `base` clashes with `base.button`'s "unstyled part" meaning. A bare tag says nothing.

C: It reads well at first: the sheet changes with the same thing `platform.ios` tests. But the two uses can be confused. `platform.ios` is a true/false value and `platform.sheet` is a component, on the same object. A reader might try `<platform.ios>` as a tag, or read `platform.sheet` as a flag. It also blurs where things come from: a UI component comes out of the device-features package, not `@markless/ui`. And it raises a question it doesn't answer: is the sheet chosen when the app is built, or checked while the page runs, the same way as the flag?

D: SY, or PF as a close second. I'd write one tag with no three-way branching and no repeated content, so changing the heading means one edit, not three. `system` keeps the UI separate from the platform flags. PF would be equally pleasant to write, apart from the flag clash.

E: No answers changed, but my confidence moved a little. Q5 stays at three places for IA; every other version needs one, which shows the cost of IA. Q3: BC strengthened my reading that `base` means "unstyled, the author styles it", so I'm more confident the drawer and `base.button` are styled by the page while `web.*`/`ios.*` are drawn by the system. Q2 and Q6: every version still uses `platform.ios` for the library note, so I still lean towards it meaning the iPhone app build, not Safari on an iPhone. That remains unconfirmed.

Tools used: none
