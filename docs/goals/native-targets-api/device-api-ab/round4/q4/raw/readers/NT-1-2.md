## Ranking
1. IA — Clearest on every point asked. Each platform branch names its source (`ios.camera`, `android.sheet`, `web.sheet`). The `@else` shows exactly what the website gets, and `ios.`/`android.` show the system draws them. The cost is that the sheet body is written three times.
2. NT — `native.` plainly says "the operating system draws this," and the `ui` import shows the source. What the website gets is left unsaid.
3. SY — Reads almost like `native`. "System" could mean the operating system, but also a design system or Markless's own default styling, so it is a bit vaguer. What the website gets is also left unsaid.
4. PF — "Drawn by the platform" comes through. But the tags come from `@markless/device`, not the component package, which is unexpected. The same `platform` object both answers questions (`platform.ios`) and draws components (`platform.sheet`).
5. BC — Misleading. `base.button` on the same page is clearly a basic part the author styles, so `base.sheet` reads as author-styled too, not system-drawn.
6. BT — Least clear. `<camera>` and `<sheet>` look like HTML or unknown custom elements, nothing is imported for them, and `<camera>` clashes in name with the imported `camera()` function. Nothing tells you who draws them or what the web gets.

B: `native` is the best single word, because in mobile development "native" already means "the operating system's own control, not drawn by the page." Per-platform `ios`/`android`/`web` is even more explicit, but it is a branching scheme, not a name. `system` comes close but could mean a design system. `platform` collides with the platform-detection object. `base` already means "unstyled building block" on this page. A bare tag says nothing at all.

C: It can be confused. `platform.ios` is a yes/no question about where the code is running, while `platform.sheet` is a component. Seeing them side by side, a reader may wonder whether `platform.sheet` is also a check, or whether `platform.ios` is a component. It also suggests `platform.camera` is somehow linked to the `camera()` function from the same package. One object doing both jobs makes both harder to read.

D: I would rather write NT. It is one tag per feature with no repeated sheet body, the name says the system draws it, and it is imported from the component package like the other tags. IA is clearer to read, but tripling the sheet body means every change has to be made three times, as the heading in question 5 shows. I would want NT plus documentation, or a type hint, saying what `native.*` renders on the web.

E: Yes, on two answers. For question 2, IA's `web.camera`/`web.sheet` branch makes me more confident that the website gets a browser stand-in rather than nothing, and that `native.*` probably picks the right version for each platform. I would move from 2 out of 5 to about 3 out of 5. For question 6, in IA `platform.ios` chooses `ios.camera`, which only makes sense inside the iPhone app. So `platform.ios` most likely means the iPhone app build, and someone using Safari on an iPhone would not see the note. I would move from 2 out of 5 to about 3 out of 5, and it is still not certain. My answers to questions 1, 3, 4 and 5 are unchanged.
