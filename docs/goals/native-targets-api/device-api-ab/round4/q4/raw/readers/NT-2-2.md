## Ranking
1. IA — This is the only version that answers all three things in the code itself. `ios.*`, `android.*` and `web.*` each say where the tag comes from, show that each platform supplies its own, and show that the website gets `web.camera` and `web.sheet`. It is the clearest to read but the worst to maintain: the sheet's contents are written out three times.
2. NT — `native.` says plainly that the operating system draws the tag, and the import shows it comes from `@markless/ui`. What the website gets stays hidden, because "native" on the web is an open question.
3. SY — `system.` means roughly what `native.` means and works almost as well. It is a little vaguer, since it could suggest "framework system components" or "design system", but it still reads as "not drawn by the page".
4. PF — `platform.camera` suggests "whatever this platform provides", which is accurate. But `platform` comes from `@markless/device`, not `@markless/ui`, so it is unclear which package owns the tag. The same object also holds the `platform.ios` flag, so a tag and a boolean share one namespace.
5. BC — `base.` is already used for `base.button`, which looks like an unstyled building block styled by the author. Putting the camera and sheet there suggests the author styles them, which is the opposite of "the system draws it". Nothing hints at what the website gets.
6. BT — Bare `<camera>` and `<sheet>` have no import, so they could be HTML, custom elements or built into Markless. A reader can't tell where they come from or who draws them, and `<camera>` could be mistaken for the `camera` function imported from `@markless/device`.

B: `native` is the best name. In app development it already means "a real operating-system view rather than a web or custom-drawn one", so it says "drawn by the platform" without any explanation. Per-platform `ios`/`android`/`web` is more exact but makes the author branch and repeat code, and it doesn't express "the system draws it" as one idea. `system` is a close second. `platform` mixes up facts about the device with components. `base` signals "unstyled building block". A bare tag says nothing at all.

C: It can be confused. `platform.ios` is a true/false value read inside `@if`, while `platform.sheet` is a component used as a tag. Readers have to work out from context which members are flags and which are tags. That invites mistakes such as `<platform.ios>` or `@if (platform.sheet)`. It can also make `platform.sheet` look like "the sheet for the current platform only", or look like it ties the sheet to whatever `platform.ios` checks. And because the tags come from `@markless/device` instead of `@markless/ui`, it blurs which package owns the components.

D: I would rather write NT. It is one tag per feature with no branching, and the content is written once (one place to edit the heading, versus three in IA). `native.` also tells the next reader that the operating system draws it. The website fallback would need documenting, but that cost is paid once in the docs instead of in every page.

E: Yes, two answers. For question 2, IA shows that `web.camera` and `web.sheet` exist, which makes it more likely that NT's `native.*` tags also have a web version rather than vanishing. I would raise my confidence there from 2 to 3 out of 5. For question 6, IA uses `platform.ios` to choose `ios.camera` over `web.camera`. If `platform.ios` were true in Safari on an iPhone, the website would try to render the iOS-only camera. That suggests `platform.ios` means the iPhone app build, so the note shows only in the iPhone app. My confidence goes from 2 to 3 out of 5, still inferred rather than confirmed. My answers to questions 1 and 3 to 5 for NT are unchanged. Comparing with IA also shows that NT's single heading (one place to edit) is a real advantage.
