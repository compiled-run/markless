## Ranking
1. IA: Each tag names its source and the platform it's drawn for (`ios.`, `android.`, `web.`), and the `@else` branch shows exactly what the website gets (`web.camera`, `web.sheet`). The cost is that the sheet body is written three times, so the heading has to change in 3 places.
2. NT: `native.` clearly says "the OS draws this, not the page" and keeps one copy of each tag. It doesn't say what the website gets, so you have to guess at a fallback.
3. SY: `system.` reads almost as well as `native.` ("the system draws this"). It's slightly vaguer, since "system" could mean a design system, the OS or the framework, and it is equally silent about the web.
4. PF: `platform.camera` hints that the platform draws it. But it puts tags into the device package's `platform` object, which elsewhere answers "which platform am I on?". It also raises a question: why does a `@markless/device` object render components when `@markless/ui` holds the components?
5. BC: `base.camera` sits next to `base.button`, which reads as the headless, page-styled family. That suggests the page draws the camera and sheet, which is the opposite of the intent. It's also odd that `base` covers both a button and a camera.
6. BT: Bare `<camera>` and `<sheet>` have no import and look like HTML or custom elements. You can't tell who supplies them or who draws them, and nothing hints at what the website does.

B: `native` is the best of the single names. In app development it already means "drawn by the OS's own UI toolkit, not by a web view", and that contrast is exactly what this page needs: `native.sheet` next to the page-drawn `drawer`. `system` is a close second, but "system" could also mean a design system. `platform` collides with the platform-detection object. `base` suggests unstyled building blocks the page styles itself, which is the opposite. Per-platform names are the most exact, but they make you branch and repeat code. A bare tag says nothing at all.

C: It could be confused. `platform.ios` is a yes/no question ("am I on iOS?"), while `platform.sheet` is a component. A reader might take `platform.sheet` as a value, or as an iOS-only sheet. Or they might expect `platform.ios.sheet` to exist. One object mixes "which platform is this?" and "the platform's own UI", and the line between them is invisible. It also blurs the package split: is UI in `@markless/device` or in `@markless/ui`?

D: I'd rather write NT. There's one tag, one copy of the sheet body and the heading changes in one place, and the name says the OS draws it. I'd want IA's per-platform names only as an escape hatch for when one platform really needs different code. I'd want NT's documentation, or a short type comment, to state what the website gets, because that is the one thing IA makes clearer.

E: Yes, two answers changed.

Question 2: IA has a `web.camera` and a `web.sheet`, which makes it much more likely that NT's `native.camera` and `native.sheet` also produce real web fallbacks rather than nothing. My confidence goes from 2 to 3 out of 5.

Question 6: In IA, `platform.ios` picks `ios.camera` and `ios.sheet`, which only make sense inside the iPhone app. The website goes to `web.*` in the `@else`. That strongly suggests `platform.ios` means "the iOS app build", not "the device runs iOS". So the note is shown to iPhone-app users only, not to Safari visitors on an iPhone. My confidence goes from 3 to 4 out of 5.

My answer to question 5 for NT stays at 1 place; it would be 3 places in IA.
