## Ranking
1. IA — It is the only version where the website's share is written in the code: `web.camera` and `web.sheet` sit in the `@else` branch. `ios.*` and `android.*` make "drawn by that OS" unmistakable, and every tag is visibly imported from `@markless/ui`. The cost is verbosity: the sheet body appears three times, so "Choose a filter" would need three edits.
2. NT — `native.` says "drawn by the OS, not the page" in one word, and the import shows it comes from `@markless/ui`. It still leaves open what the website gets: a "native" sheet in a browser is a guess.
3. SY — `system.` signals the same thing as `native`, but it is weaker. Next to `base` and `drawer` in a UI package, "system" can also read as "design system", and it says nothing about the website.
4. PF — `platform.` does suggest something drawn by the platform. But the same object also holds the `platform.ios` check, and the tags come from `@markless/device` while every other component comes from `@markless/ui`. That makes the source and the meaning harder to pin down. It says nothing about the website.
5. BC — `base.` sits beside `base.button`, which reads as a page-styled, headless (behaviour-only, no built-in look) primitive. That suggests the author draws the camera and the sheet, which is the opposite of the intended meaning.
6. BT — Bare `<camera>` and `<sheet>` have no import. They look like HTML or unknown custom elements, so there is no way to tell where they come from, who draws them, or what the website gets.

B: `native` names it best. The word itself means "the platform's own widget, not ours", developers know it from React Native and "native UI", and it doesn't clash with anything else on the page. The per-platform `ios`/`android`/`web` names are even more explicit, but they force a three-way branch at every use and copy the body three times; they are better kept as an escape hatch. `system` is the runner-up but can be read as "design system". `platform` is overloaded (see C). `base` points the wrong way. A bare tag says nothing.

C: It could be confused. `platform.ios` is a true/false value and `platform.sheet` is a component on the same object, so a reader can't tell from the name which members are flags and which are tags. It also suggests that `platform.sheet` might depend on `platform`'s current value, something like "the sheet for the current platform, if there is one". That made me wonder whether it renders at all on the website. It also hides the fact that this is a UI component living in the device package. Readers have to tell the members apart by case and by tag position alone.

D: I'd rather write NT. It is one tag per use with one body, so changing "Choose a filter" is a single edit. The name states who draws it, and the import keeps all components in `@markless/ui` while `@markless/device` keeps device facts like `platform.ios`. I'd want the `native.*` docs or types to state the website fallback. I'd use IA-style per-platform tags only where one platform truly needs different content.

E: Yes, IA changed two answers and strengthened a third. For question 2, IA's `web.camera` and `web.sheet` branch suggests the website does get a real camera preview and sheet. That raises my confidence that `platform.camera` and `platform.sheet` have web fallbacks rather than rendering nothing, from 2/5 to about 3/5. For question 6, IA uses `platform.ios` to choose between `ios.*` and `web.*` tags, which only makes sense if `platform.ios` means the iPhone app build. So Safari on an iPhone would get the web branch. That strengthens my "only the iPhone app" answer, from 3/5 to about 4/5. For question 1, the other versions put the native tags in `@markless/ui`. My answer for PF (from `@markless/device` through `platform`) stands, but it now looks like PF is the odd one out rather than the norm. My answer to question 5 for PF (one place) is unchanged; in IA it would be three places.
