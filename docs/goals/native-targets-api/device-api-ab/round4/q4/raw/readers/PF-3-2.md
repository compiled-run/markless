## Ranking
1. IA — It is the only version that shows all three answers in the code. `ios.*`, `android.*` and `web.*` come from `@markless/ui`, each branch names its platform, and the `@else` branch shows the website gets `web.camera` and `web.sheet`. The cost is that the sheet and its contents are written out three times, which makes it the worst to maintain.
2. NT — `native.*` from `@markless/ui` reads most plainly as "the platform draws this". It sits apart from `platform.ios`, which stays as the only "which platform am I on?" question. It does not say what the website gets: "native" on the web could mean the browser's own controls or nothing.
3. SY — This reads almost like NT. It is also from `@markless/ui` and kept apart from `platform`. But "system" could also mean operating-system screens such as share sheets, pickers or permission prompts, rather than "the platform's own version of a control". It says nothing about the website either.
4. PF — "platform" does suggest platform-specific. But the tags come from the device package, and one `platform` object is both a set of components and an "am I on iOS?" check. That makes it easy to read `platform.sheet` as "only exists on some platforms", and it says nothing about the website.
5. BC — `base` is already the namespace for `base.button`, which the page styles itself. So `base.camera` and `base.sheet` read as more page-drawn building blocks, which is the wrong message. Nothing signals that the system draws them.
6. BT — Bare `<camera>` and `<sheet>` look like HTML or custom elements. `sheet` is never imported. `camera` is imported as the function behind `cam = camera()`, so `<camera>` seems to reuse a function name as a tag. The reader can't tell the source, the drawer or the website result.

B: `native` is best. It is the common word for "drawn by the platform, not by the page", it goes in a component namespace, and it doesn't collide with checking which platform you're on. Per-platform `ios`/`android`/`web` is the most explicit, but it names the platform rather than the fact that the platform draws it, and it pushes branching onto every page. `system` comes close but overlaps with system screens. `platform` overlaps with the platform checks. `base` suggests the opposite. A bare tag says nothing.

C: It can be confused. `platform.ios` is a yes/no value and `platform.sheet` is a component, but both have the same shape. A reader can take `platform.sheet` to be a condition ("does this platform have sheets?"), or take `platform.ios` to be an iOS-only component. It also blurs whether `platform.*` tags are fixed per build or chosen at run time, which in turn blurs whether `platform.ios` means the iOS app or any iOS device. Questions 2 and 6 turned on exactly that.

D: I'd rather write NT. It's one tag per feature with no branching, and the name says the platform draws it. It keeps "which platform am I on?" (`platform.ios`) separate from "use the platform's own control" (`native.sheet`). I would want the docs to state what `native.*` renders on the website. IA is clearer to read but triples the sheet's contents and invites the three copies drifting apart.

E: Yes, two answers became more confident, though the code I was given (PF) didn't change.

Question 2: IA shows that `web.camera` and `web.sheet` exist. That supports my guess that the website gets a browser camera preview and a web-drawn sheet rather than nothing. I'd raise my confidence from 2 to 3 of 5.
