## Ranking
1. IA: The branches say outright which tag each platform gets, including `web.camera` and `web.sheet` for the website, and the `ios`, `android` and `web` names make it obvious the platform draws each one. The cost is that the sheet body is written three times.
2. NT: `native` clearly means "drawn by the operating system". The website is left implicit: you have to guess that there is a web fallback.
3. SY: `system` reads as "the OS draws this", but it could also be read as "the design system". You still have to guess what the website gets.
4. PF: The import shows the tags come from `@markless/device`, and `platform` suggests the platform draws them. But the same `platform` object also holds the `platform.ios` flag, so a tag and a yes/no check share one name. It is also odd that these tags come from the device package while `drawer` comes from `@markless/ui`.
5. BC: `base` is the same namespace as `base.button`, which looks like a toggle the page styles itself. So `base.camera` and `base.sheet` read as plain building blocks the author styles, which is the opposite of "the system draws it".
6. BT: The bare `<camera>` and `<sheet>` have no import, so they look like HTML or custom elements. Nothing tells you where they come from or who draws them.

B: `native`. It is the one word that plainly means "the operating system's own widget, not something the page drew". `system` comes second, because it can be confused with the design system. The per-platform `ios`/`android`/`web` names are the most precise, but they make you repeat code and you lose the single tag. `platform` is overloaded with the flags. `base` suggests unstyled building blocks, and a bare tag says nothing at all.

C: It can be confused. `platform.ios` is a yes/no value and `platform.sheet` is a component, yet they look alike as `platform.x`. A reader might wonder whether `platform.ios` is also a tag, or whether `platform.sheet` is a yes/no check ("does this platform have a sheet?"). It also leaves open whether `platform.sheet` changes depending on `platform.ios`. The two meanings, "which platform am I on" and "the platform's widgets", should not share one object.

D: NT. One tag works everywhere, the name says the OS draws it, and the heading text lives in one place. I would write IA only if I needed different content on each platform.

E: Yes, two answers changed. For question 6, IA's `@if (platform.ios) … @else { web.* }` only makes sense if `platform.ios` is false on the website. Otherwise iPhone Safari would try to show `ios.camera`. That strengthens my reading that only people in the iPhone app see the note, so my confidence goes from 3 to 4. For question 2, `web.camera` and `web.sheet` existing makes it more likely that `system.camera` and `system.sheet` fall back to web versions on the website, so my confidence goes from 2 to 3. My answers to questions 1, 3, 4 and 5 are unchanged.
