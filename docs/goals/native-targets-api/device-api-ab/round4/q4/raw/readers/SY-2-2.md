## Ranking
1. IA: The clearest about where each tag comes from and what the website gets. `web.camera` and `web.sheet` are spelled out in an `@else`, so the reader can see the website gets a web version, and `ios.`/`android.` say the phone's own component is used. The cost is that the sheet's contents are written three times.
2. NT: `native.` plainly says "the platform draws this, not the page." It is one tag, and its source (`@markless/ui`) is clear from the import. What the website gets is still a guess, and "native" on a website is a bit contradictory.
3. SY: Close to NT, but "system" is vaguer. It could be read as a design system or as system screens (settings, permissions) rather than "the OS draws it." The website behaviour is also a guess.
4. PF: "Platform draws it" reads fairly well. But the tags come from `@markless/device`, a package of device features, not UI. It also shares an object with the `platform.ios` flag, which confuses the two kinds of thing.
5. BC: `base.camera` sits beside `base.button`, which is a page-styled headless component. That suggests the page draws and styles the camera and sheet too, which is the opposite of the intended meaning.
6. BT: Bare `<camera>` and `<sheet>` look like HTML elements, though neither is HTML. Nothing is imported for them, so the source is invisible, and nothing says the platform draws them or what the website gets.

B: `native` is the best fit, because it is the everyday word developers already use for "the OS's own UI, not ours." `ios`/`android`/`web` say it even more precisely, but they force a branch at every use. `system` is second: it is plausible but could mean "design system." `platform` mixes up "which platform am I on" with "the platform's component." `base` suggests the opposite, a component the page styles. A bare tag says nothing.

C: It can be confused. `platform.ios` is a true/false flag and `platform.sheet` is a component, yet they are written the same way. A reader could take `platform.ios` for a tag, or `platform.sheet` for a feature-detection flag. The shared object also hides a contradiction: UI tags are coming from the device-features package. A third wrinkle: `platform.sheet` could be read as "a sheet for the current platform only," as if it existed only where `platform.ios` or `platform.android` is true. That makes its website behaviour even less clear.

D: I would rather write NT. Each feature is one tag, written once, and the name says the platform draws it. IA spells everything out, but it triples the sheet's contents, so the heading would need three edits instead of one and the copies could drift apart. I would trade IA's explicitness for one line of documentation on what `native.*` does on the website.

E: Yes, for question 6 and a little for question 2. The first version was SY. In IA, the `@else` branch for the website follows `platform.ios`/`platform.android`. That only makes sense if `platform.ios` means the iPhone app build, because otherwise Safari on an iPhone would get the native `ios.camera`. So I am now more confident, about 3 out of 5 instead of 2, that only the iPhone app user sees "Photos also save to your library." IA also backs my question 2 guess that the website gets a web stand-in rather than nothing. It does not prove the single `system.*` tag does the same, so that confidence rises only slightly, to about 2.5. My question 5 answer for SY stays at one place. In IA it would be three.
