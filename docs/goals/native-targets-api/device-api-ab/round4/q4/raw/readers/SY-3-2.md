## Ranking
1. IA: This is the only version that answers all three questions directly in the code. The `@if (platform.ios) / @else if (platform.android) / @else` branches show that each platform gets its own camera and sheet, and `web.camera` / `web.sheet` say outright what the website gets. The cost is three copies of the sheet body, and the reader has to assume that `ios.*` means "drawn by iOS."
2. SY: One tag, with an import from `@markless/ui`. `system` says the operating system or browser draws it, and that covers the website too: the browser is the "system" there. What the web actually renders is still implied, not shown.
3. NT: `native` says most strongly "not drawn by the page." On a website, though, "native" reads as "native app," so a reader is more likely to assume the website gets nothing or the build fails.
4. PF: `platform` suggests the platform draws it, but the same object also holds the yes/no checks (`platform.ios`), and it comes from `@markless/device`, not the UI package. It is unclear whether `platform.sheet` is a component or a property, and where the components live.
5. BC: `base` is already the namespace for the headless `base.button`, which the page draws itself. `base.camera` and `base.sheet` read as more page-drawn parts, the opposite of what is meant. Nothing hints at native drawing or a web fallback.
6. BT: Bare `<camera>` and `<sheet>` have no import. They look like HTML elements or framework built-ins, and `sheet` is not real HTML. You cannot tell where they come from, who draws them, or what the web gets.

B: `system` is the best name. It says "drawn by the OS or browser, not by the page," and it stays true on the web, where the browser is the system. `native` makes the platform-drawn point slightly more strongly, but it suggests "app only" and leaves the website unclear. Per-platform `ios`/`android`/`web` is the most explicit, but it forces branching and duplicated code. `platform` mixes components with the yes/no checks. `base` contradicts the existing headless `base.*`. A bare tag hides where it comes from.

C: It reads poorly. `platform.ios` is a yes/no check and `platform.sheet` is a component, side by side on one object. Several confusions are easy:
- A reader could think `platform.sheet` is also a check ("does this platform support sheets?").
- A reader could think `platform.ios` is a component.
- A reader could think the sheet changes with whichever `platform` value is active.

Also, the object comes from `@markless/device`, so the UI components seem to live in the device package, away from the rest of the UI.

D: I would rather write SY: one tag, one import, no branching, and the name says who draws it. I would want the docs to state clearly what each `system.*` tag renders on the web. IA is clearer to read but painful to keep up: three copies of the sheet body to keep in sync.

E: Yes, two answers got firmer, but the evidence is indirect:
- Question 2 (website build): IA has `web.camera` and `web.sheet`, which suggests web versions exist. That makes my guess more likely: on the website, `system.camera` shows a browser camera preview and `system.sheet` a web-drawn sheet.
- Question 6 (`platform`): IA pairs `platform.ios` / `platform.android` with an `@else` that goes to `web.*`. That suggests `platform.ios` means the iPhone app, not iOS Safari. So my "iPhone app only" reading for the library note gets a bit more likely. My confidence on question 6 goes from 3/5 to about 3.5/5. It still could mean the operating system.

My answers to questions 1, 3, 4 and 5 are unchanged.
