# A tap's click count on a phone's browser (measured 2026-11-19)

editable's trigger opens a session from its click handler, reading `event.detail`, the click count, so that
`editOnDoubleClick` can ask for a double click. Measured on this Mac with `receipts/2026-11-19-tap-count.html` (two
buttons, the second with `touch-action: manipulation`, logging `pointerdown`, `pointerup`, `click` and `dblclick` with
`detail`), raw events in `receipts/2026-11-19-tap-count.json`:

| | iOS Safari 27.2 (simulator, Maestro `tapOn` and `doubleTapOn`) | Android Chrome 133 (AVD, `adb shell input tap`) |
|---|---|---|
| One tap, then another two seconds later | `click` with `detail` 1, then 1 | the same |
| Two quick taps (about 200 ms apart on iOS, 7 ms on Android) | `click` 1, `click` 2, `dblclick` 2 | the same |
| Two quick taps on `touch-action: manipulation` | `click` 1, `click` 1, no `dblclick` | `click` 1, `click` 2, `dblclick` 2 |

The longest gap that still counts as a second click was not measured on either phone.

## What native hosts do to match

A press's `click` handler reads `event.detail` as the number of presses in a row: 1, then 2 for a second quick press,
and so on. On iOS that is UIKit's own count of quick taps in one place (`UITouch.tapCount`); on Android, a second press on
the same view within `ViewConfiguration.getDoubleTapTimeout()`, the double-tap time Chrome's gesture detector also uses.
`touch-action: manipulation` is not read: editable, the family whose trigger reads `detail`, does not set it.
