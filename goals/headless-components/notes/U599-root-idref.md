# An IDREF on a widget root's own element: measured, and one file short

Status: **blocked**. The compiler refusal is lifted and the witness is built, and
the witness shows exactly one thing still wrong — a root nested inside another
instance of its own family mints its element ids from the ENCLOSING instance.
Fixing that needs `packages/web/src/ssr-data/renderer.ts`, which is outside the
packet's file contract, plus retiring one pinned row in
`packages/compiler/test/semantic-idref-handles.test.ts`, also outside it.

## What the packet assumed, and what is actually true

The packet's premise — "the token naming the widget instance is not readable
from inside the root itself" — is only half true, and the half that is false is
the larger half.

The instance token is computed by the CONSUMER's seed pass, before the root
component renders at all: `packages/web/src/fns/shared-seed.ts:53-66` builds
`base + composedRoot` and files it under the plain key
`markless:widget-instance` and under `markless:widget-instance|<definitionId>`
for every family the placed child roots. The compiled SSR twin does the same at
`packages/compiler/src/passes/public-render/ssr-module.ts:755-772`. So the token
exists before the root renders, and nothing has to be minted anywhere new.

What throws it away is one function on the way back:

```ts
// packages/web/src/ssr-data/renderer.ts:679
function rootEdgeSeeds(childSeeds, inherited) {
	let restored;
	for (const [key, enclosing] of inherited ?? []) {
		if (!key.startsWith(MARKLESS_WIDGET_INSTANCE_KEY)) continue;
		if (enclosing === undefined || enclosing === childSeeds.get(key)) continue;
		(restored ??= new Map(childSeeds)).set(key, enclosing);
	}
	return restored ?? childSeeds;
}
```

It hands the widget root's OWN render the enclosing widget's instance token, on
purpose ("the ids it mints stay put while the values its parts seeded reach
it"). It is the single chokepoint for both paths: the compiled SSR module and
the CSR prerender evaluator both render through `renderSsrData`.

Consequences, all measured below:

- A root with no enclosing instance of its own family already mints correctly —
  `inherited` has no entry, so nothing is restored. The compiler refusal was
  refusing a case that works.
- A root nested inside another instance of the SAME family gets the outer token
  restored, so its own element mints the OUTER instance's ids while the parts it
  seeds mint its own. The two ends of the relationship disagree.

all with the same shape (path slug shortened here):

## The fix I could not apply

In `rootEdgeSeeds`, restore only the plain fallback key and leave the
per-definition keys as the pass filed them:

```ts
	for (const [key, enclosing] of inherited ?? []) {
		if (key !== MARKLESS_WIDGET_INSTANCE_KEY) continue;
		if (enclosing === undefined || enclosing === childSeeds.get(key)) continue;
		(restored ??= new Map(childSeeds)).set(key, enclosing);
	}
```

Why this is the whole change, and why it is safe:

- A per-definition key is written by the seed pass only for a family the placed
  child ROOTS (`shared-seed.ts:61-62`, `ssr-module.ts:769-772`); nothing else
  writes one. So a per-definition key whose value differs from the enclosing map
  is, by construction, a family this child roots — exactly the case that must
  keep its own token. Skipping every per-definition key is therefore identical to
  skipping only the rooted ones, and needs no new information at the call site.
- A family the child does NOT root already has `enclosing === childSeeds.get(key)`
  and was never restored, so nothing moves for it.
- The plain key keeps returning to the enclosing widget, so an element carrying a
  handle of a family with no per-definition token behaves exactly as today.
  `widgetInstanceReadSource` (`residue-reader.ts:180`) asks the per-definition key
  first and falls back to the plain one, so the precise answer wins where it
  exists.
- No new seed key, no new constant, no compiler emit change: the SSR module and
  the CSR reader already spell the per-definition read.

I did not apply it, and did not try a route around it. The alternatives I
measured against the contract all fail: the mint's key expression is built in
`packages/compiler/src/passes/public-render/residue-reader.ts` and is called from
`ssr-module.ts` (in contract) AND from the client reader in `residue-reader.ts`
itself (not in contract), so a new key would fix SSR and leave CSR wrong; and the
CSR seed pass cannot defeat the restore without mutating the caller's map, which
would corrupt the enclosing instance for every sibling part rendered after it.

## What this unblocks for menu

Both attributes the `menu.item` > `menu.itemcontent` ruling asks for compile now:
`aria-controls={item.itemContentEl}` on the item and
`aria-labelledby={item.itemEl}` on the itemcontent. Once the renderer line lands,
both resolve per instance at every depth, so the `menu.itemlabel` part is no
longer forced on the family and `aria-controls` on a nesting item no longer has to
be dropped. The two owner decisions the U596 memo raised can be reopened on the
merits rather than settled by a compiler wall.
