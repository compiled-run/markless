# Waiting is a block, not a flag

<PageMeta time="3 min" assumes="state, computed, conditionals" />

Count the variables a loading spinner usually needs. The data. A flag for "still loading". An error,
in case the data never comes. Then a rule in your head about which one wins when two are set.

Only the data is what the page is about. You can drop the other three.

**Give `computed()` an `async` recipe. Then write three blocks: one for the answer, one for the
wait, and one for a failure.**

## Pick a mug

<AsyncSketch />

In the card above, pick a mug, then another. The old answer stays on the page until the new one is ready.

In the code below, press **Tall mug** and wait a moment. Press **Small mug**. Then press **Cracked
mug**.

<Code note="Delete the @catch block and pick the cracked mug. Then change the return line to return { text: (await loadMugFact(mug)) + mug }; and pick again.">
```tsrx title="mug-facts.tsrx"
import { computed, state } from '@markless/core';
import { loadMugFact } from './mug-facts.ts';

export default function MugFacts() @{
	let mug = state('');
	const fact = computed(async () => {
		return { text: await loadMugFact(mug) };
	});

	<section>
		<button onClick={() => (mug = 'tall')}>
			Tall mug
		</button>
		<button onClick={() => (mug = 'small')}>
			Small mug
		</button>
		<button onClick={() => (mug = 'cracked')}>
			Cracked mug
		</button>
		@try {
			<p>{fact.text}</p>
		} @pending {
			<p>Looking it up...</p>
		} @catch {
			<p>That mug is not on the shelf.</p>
		}
	</section>
}
```

```ts title="mug-facts.ts"
const facts: Record<string, string> = {
	tall: 'The tall mug holds a big coffee.',
	small: 'The small mug holds one espresso.',
};

export function loadMugFact(
	mug: string,
): Promise<string> {
	if (mug === '') {
		return Promise.resolve('Pick a mug.');
	}
	return new Promise((resolve, reject) => {
		setTimeout(() => {
			const fact = facts[mug];
			if (fact) {
				resolve(fact);
			} else {
				reject(new Error(`No mug called ${mug}`));
			}
		}, 1500);
	});
}
```
</Code>

Each pick runs the recipe again. When the answer is ready, it swaps in. The cracked mug fails: the
last answer stays on the page, and the `@catch` block shows up right after it. Pick another mug and
the `@catch` block goes away.

`loadMugFact`, in the `mug-facts.ts` tab, stands in for a `fetch`. It answers "Pick a mug." straight
away, waits before it answers anything else, and fails for a mug it does not know.

## The three blocks

`@try` holds what you show once the value is ready. Inside it, read the value directly, as in
`fact.text`. There is no `.data` to reach through and no status to check. The type says the same:
`computed(async () => ({ text: '' }))` is typed `{ text: string }`, the resolved value, not a promise.

`@catch` holds what you show when the recipe throws or its promise rejects. On the first load it is
the only thing shown. After that, the last answer stays and `@catch` shows right after it.

`@pending` holds what you show while there is no answer yet. That is the first load: once an answer
is on the page, picking again keeps it there while the next answer loads.

A `@try` needs a `@pending` or a `@catch` after it, or both. Each block holds one node. For more,
wrap them in a fragment: `@try { <><h2>{fact.text}</h2><p>More</p></> } @pending { <p>Loading</p> }`.

## Watch a spot wait

The parcel is `arrives`, a value still on its way. Until it lands, the `@pending` words hold its spot in pencil, and the rest of the page is already there. When the answer comes back down the wire, only that spot is inked in.

## While a new answer loads

While the next answer loads, Markless puts `aria-busy="true"` on each element that shows that
value, so you can style it, for example `[aria-busy='true'] { opacity: 0.5; }`. That covers text,
attributes, a list built from the value, a value passed to a child component, and values computed
from it. A picker or checkbox in the same block that reads only plain state is never marked. If a
block shows two async values, each one marks its own elements, and each mark goes away when its
own answer, or the `@catch` block, is on the page.

Values shown together stay matched while the new answer loads. Say a figure divides a total by
the number of days you picked. Pick a longer range, and until the new total arrives the figure keeps
using the old range, so it never shows the old total divided by the new days. A setting the request
does not use, such as a currency the page converts itself, applies at once. An event handler reads
the same pair the page shows, so a Share button shares the figure next to the range it was
fetched for.

Text that reads only the setting, not the answer, does not wait. `<p>Sorted by {sort}</p>` next to
a list fetched with `sort` shows the new order above the old list until the new list arrives. The
build warns about this with `MARKLESS_ASYNC_INPUT_BESIDE_VALUE`. Return the setting along with the
data and show it from there, as `{posts.sort}`. A picker or button that sets `sort` is fine as it
is: it shows the choice the user just made.

To compare the old answer with what the user just typed, keep two states: one the request reads,
one it does not. The one it does not read always shows the latest value.

```tsrx
import { computed, state } from '@markless/core';
import { loadMugFact } from './mug-facts.ts';

export default function MugSearch() @{
	let typed = state('tall');
	let asked = state('tall');
	const fact = computed(async () => {
		const mug = asked;
		return { mug, text: await loadMugFact(mug) };
	});

	<section>
		<input value={typed} onInput={(event) => {
			typed = event.currentTarget.value;
			asked = event.currentTarget.value;
		}} />
		@try {
			<p class={fact.mug !== typed ? 'old' : ''}>{fact.text}</p>
		} @pending {
			<p>Looking it up</p>
		}
	</section>
}
```

`fact.mug !== typed` is true while a newer answer loads, because the request never reads `typed`.

`@pending` only comes back if the newest request has been waiting for more than 5 seconds. Each new
pick starts that wait over, so fast typing never brings it back.

Screen reader users hear about it too. When a block keeps its content and marks it busy, Markless
says "Updating…" through a hidden status message, then "Updated", or "Update failed" when the
`@catch` block shows instead. A first load says nothing, and a burst of quick changes, such as
typing, is said once. The message lives outside the page content, because some screen readers,
NVDA in Firefox for one, stay silent about messages inside a busy element.

To say something else, put the block inside an element with `aria-live` or `role="status"` and
write your own message there. Markless then leaves that block to you. `aria-live="off"` on that
element turns the message off.

In the editor, hover `@try` or an async value to see what happens there on a refresh: which input
starts it, which elements are marked busy, and which input the shown text stays matched to.

## A background refresh stays quiet

Not every refresh is something the person on the page asked for. A page that polls for new orders
every 30 seconds, or updates a figure when a message arrives over a socket, refreshes the block
without anyone clicking anything. Markless tells these apart by where the write that changed the
answer came from, not by anything you write:

```tsrx
import { computed, state } from '@markless/core';
import { fetchOrders } from './orders.ts';

export default function Orders() @{
	let poll = state(0);
	const orders = computed(() => {
		const key = poll;
		return fetchOrders();
	});

	setInterval(() => poll = poll + 1, 30_000);

	<button onClick={() => poll = poll + 1}>Refresh now</button>
	@try {
		<ul>{orders.rows.map((row) => <li>{row.title}</li>)}</ul>
	} @pending {
		<p>Loading orders</p>
	}
}
```

The timer bumps `poll` every 30 seconds, and the button bumps the same state when someone clicks
it. Markless watches where the write happens, not which state it touches:

- A write inside an event handler — the button's `onClick`, including anything it does after an
  `await` — marks the block busy and says "Updating…", exactly as the rest of this page describes.
- A write anywhere else — a `setInterval`/`setTimeout` callback, a socket or `EventSource`
  message, a promise that no handler started — refreshes the block quietly: no `aria-busy`, no
  announcement, and the list on the page still never flickers back to "Loading orders" while the
  old one is replaced in place.

A quiet refresh that fails is the one exception: Markless still says "Update failed", because a
poll that silently stopped working is worse than one that occasionally speaks up. The list itself
follows the same [failed-refresh rule](#try-again) either way — it keeps showing the last good
orders, and `@catch` opens right after them.

## Try again

Name a second value in `@catch` and you get a function that runs the failed recipes of that block
again, with the same inputs. Hand it to a button:

```tsrx
import { computed } from '@markless/core';
import { loadMugFact } from './mug-facts.ts';

export default function MugFact() @{
	const fact = computed(async () => {
		return { text: await loadMugFact('cracked') };
	});

	<section>
		@try {
			<p>{fact.text}</p>
		} @catch (error, reset) {
			<>
				<p>{error.message}</p>
				<button onClick={reset}>Try again</button>
			</>
		}
	</section>
}
```

While it runs again, the `@catch` block stays on the page, marked busy. When an answer comes back,
the `@try` block takes its place.

A block inside another block catches its own failures. If only the inner one fails, its `@catch`
shows inside it, and the outer block keeps showing what it had.

Write `@catch` right after a `@try` block. Written after an element, it is just text on the page, so
the build stops with `MARKLESS_ASYNC_CATCH_WITHOUT_TRY`.

## Load it again

A recipe runs again when a state it reads changes. To load the same thing again, after a save or
from a Reload button, give the recipe a counter to read and add one to it:

```tsrx
import { computed, state } from '@markless/core';
import { loadMugs, saveMug } from './mugs.ts';

export default function MugShelf() @{
	let reload = state(0);
	const mugs = computed(async () => {
		reload;
		return await loadMugs();
	});

	<section>
		<button onClick={() => reload++}>Reload</button>
		<button onClick={async () => {
			await saveMug('tall');
			reload++;
		}}>Add a tall mug</button>
		@try {
			<ul>
				@for (const mug of mugs; key mug.id) {
					<li>{mug.name}</li>
				}
			</ul>
		} @pending {
			<p>Counting mugs</p>
		}
	</section>
}
```

The bare `reload;` line is the read: it is what makes a change to `reload` run the recipe again.
Adding one is a refresh like any other: the list stays on the page, marked busy, until the new one
arrives.

## One block per row

To give each row of a list its own wait, put the async value in a component and render that
component in the row. Each row then has its own `@try`, so one slow or failing row does not hold up
the others:

```tsrx
@for (const list of lists; key list.id) {
	<section>
		<TodoList tag={list.tag} />
	</section>
}
```

A row added after the page loads gets its own copy of the component. Its `@pending` block shows,
then its own answer. When the recipe runs again, it reads that row's `tag`.

To start over when a choice changes, key a one-row list by the choice. A new value is a new key, so
the old row goes away and the new one starts from its `@pending` block:

```tsrx
@for (const topic of [subject]; key topic) {
	<Feed topic={topic} />
}
```

Each row of a list must be one element, so `Feed` wraps its `@try` in one:

```tsrx
export default function Feed({ topic }: { topic: string }) @{
	const posts = computed(async () => await loadPosts(topic));

	<section>
		@try {
			<p>{posts.length} posts about {topic}</p>
		} @pending {
			<p>Loading...</p>
		}
	</section>
}
```

Without the `<section>`, the build stops with `MARKLESS_KEYED_REPEAT_ROW_NOT_ONE_ELEMENT`.

## Read state before or after an await

A recipe can read state anywhere, before or after an `await`. Markless reads every state the recipe
names when the recipe starts, and runs it again when any of them changes, even while it is still
waiting for an answer.

One read stops the build with `MARKLESS_ASYNC_POST_AWAIT_READ`: a lookup whose key is the answer
itself, like `shelf[(await loadPick()).id]`. Markless cannot know which entry that is until the
answer arrives. Return the answer from the recipe, and do the lookup in a second, plain
`computed()`.

## Build errors inside `@try`

These shapes stop the build:

| Shape | Code |
| --- | --- |
| Two nodes side by side in a `@try`, `@pending` or `@catch` block | [`MARKLESS_BLOCK_SIBLING_NODES`](/errors/MARKLESS_BLOCK_SIBLING_NODES) |
| A `@try` with neither `@pending` nor `@catch` after it | `MARKLESS_PARSE_ERROR` (TSRX1010) |
| A read of the async value outside every `@try` | [`MARKLESS_ASYNC_BOUNDARY_REQUIRED`](/errors/MARKLESS_ASYNC_BOUNDARY_REQUIRED) |
| `@pending` written after `@catch` | [`MARKLESS_ASYNC_ARM_ORDER`](/errors/MARKLESS_ASYNC_ARM_ORDER) |
| `@catch` after an element instead of a `@try` | [`MARKLESS_ASYNC_CATCH_WITHOUT_TRY`](/errors/MARKLESS_ASYNC_CATCH_WITHOUT_TRY) |
| A `@for` row that is not one element | [`MARKLESS_KEYED_REPEAT_ROW_NOT_ONE_ELEMENT`](/errors/MARKLESS_KEYED_REPEAT_ROW_NOT_ONE_ELEMENT) |
| A lookup keyed by the answer, like `shelf[(await loadPick()).id]` | [`MARKLESS_ASYNC_POST_AWAIT_READ`](/errors/MARKLESS_ASYNC_POST_AWAIT_READ) |

[`MARKLESS_ASYNC_INPUT_BESIDE_VALUE`](/errors/MARKLESS_ASYNC_INPUT_BESIDE_VALUE) is a warning, not
an error. [Error codes](/errors) lists every other code.

## Common questions

### Is `@catch` required?

No. A `@try` needs a `@pending` or a `@catch`, and either one is enough. Without `@catch`, a first
load that fails leaves that spot empty, and the rest of the page still shows.

### Can `@catch` take only the error?

Yes. `@catch` names nothing, `@catch (error)` names the error, and `@catch (error, reset)` also names
the [try-again function](#try-again).

### Can a click handler read the async value?

Yes. Put the button inside the `@try` and read the value as the page does:
`onClick={() => save(report.days)}`. While a new answer loads, the handler still reads the answer on
the page.

### What if an `await` inside a click handler fails?

`@catch` does not show. It only shows when a `computed()` recipe fails. The handler stops at that
`await`, state it changed before the `await` keeps its new value, and the browser reports an uncaught
error. To show the failure, catch it in the handler and keep a message in state:

```tsrx
<button onClick={async () => {
	try {
		await saveReport(report.days);
		note = 'Saved';
	} catch {
		note = 'Could not save';
	}
}}>Save</button>
```

### What if answers arrive out of order?

The newest input wins. Each change starts the recipe again, and only the run that started last can
put its answer on the page. An older run that finishes later is dropped, whether it succeeds or
fails. Your request itself is not cancelled. It runs to the end, and its answer is ignored.

### Is there a mount hook or an effect?

No. There is no `onMount`, no `useEffect` and no effect function. The component body runs once, to
set up the page. To load data when the page opens, use `computed(async …)`. For code that needs the
element itself, use [`attach`](/build/elements). For code that should wait until the page is idle,
use [`onIdle`](/concepts/events). Work that follows a change goes in the handler that makes the change.

### Is there an API reference or an example app?

There is no separate API reference page. [Every Markless package](/reference) lists what each
package exports, and the types ship with `@markless/core`: `state<T>(initial: T): T`, and
`computed()`, which gives back the resolved value for an async recipe. Each build error has a page
in [Error codes](/errors). There is no example app written for learning yet.
