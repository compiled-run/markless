# CI and the checks you run at home

<PageMeta time="4 min" assumes="nothing" />

<ThemeToggle />

<Subtitle text="pnpm ci:local reads .github/workflows/ci.yml each time it runs, so your machine runs the same commands CI does." />

```bash
pnpm ci:local --fast
```

That runs the four fast jobs. The pre-commit hook runs them too. Everything heavier runs on GitHub, where the pull request's green run is the proof.

## How it sorts the steps

`scripts/ci/local.mjs` reads every job's steps and puts each one in a group:

- **check**: a `run:` step that tests something. It runs.
- **setup**: `pnpm install`, `corepack enable` and the Playwright installs. They run only with `--install`.
- **skip**: `uses:` actions, lane cache markers, and steps that read GitHub's own context. That's CI plumbing.

The script keeps one small table that puts each job in a mode. A new job with check steps but no entry makes it stop with an error naming the job.

## The jobs

| Job | Mode | What it runs |
| --- | --- | --- |
| `agent-files` | fast | `ruler apply`, then fails if the agent files changed |
| `typecheck` | fast | `check-workflow.mjs` on `ci.yml`, `pnpm typecheck`, `pnpm exec vp check --no-fmt` |
| `typecheck-ts7` | fast | `pnpm typecheck:ts7`: the same check on TypeScript 7.1 |
| `unit` | fast | `pnpm exec vp test --project node` |
| `browser` | full | the `browser` and `ui` test projects, and the `@markless/ui` API manifest check |
| `completion-matrix` | full | the packaged editor plugin's completions |
| `boxes-bundler`, `boxes-router` | full | each package's `test:boxes` |
| `boxes-music-player`, `boxes-music-player-ssr` | full | each demo's `test:analyzer` and `test:boxes` |
| `website-boxes` | full | this site's tooling tests and `test:boxes` |
| `demo-boxes` | full | the `live-feed`, `same-module-branch` and `executed-at-load` demos |
| `perf-guards` | full | `pnpm perf:guard`: page weight and interaction budgets |
| `build-scale`, `build-warnings` | full | build budgets at two app sizes; no new build warnings |
| `package-manager-matrix` | full | the CLI's workspace detection under npm, pnpm, Yarn and Bun |
| `test` | full | the gate: fails unless every lane passed or hit its cache, then checks the analyzer receipts |
| `benchmark`, `benchmark-guard` | CI only | js-framework-benchmark against the base commit, then a compare |

`lanes`, `prepare-playwright`, `carry-queue-markers`, `save-lane-markers` and `changes` only route work. The required checks are `test`, `typecheck` and `agent-files`.

## Run it at home

```bash
pnpm ci:local --list                            # every job and step, and its mode
pnpm ci:local --fast                            # the four fast jobs (the default)
pnpm ci:local --job browser --job boxes-router  # only these jobs
pnpm ci:local --fast --clean                    # in a throwaway worktree of HEAD
pnpm ci:local --dry-run                         # print the commands, run nothing
```

- `--list` only prints.
- `--clean` uses the committed tree, so an untracked file can't make a check pass.
- `--full` runs every job this machine can run. Use it to debug, not as proof.
- `--linux` runs each job in its own `node:24-bookworm` container. It needs `docker`, and without it the script exits with code 2. `docs/ci-process.md` says this path hasn't been run yet.

## Two more workflows

- `screen-reader.yml` runs a `virtual` lane on pull requests that change `packages/headless/`, `runtime`, `web` or the compiler's markup passes. Its `nvda` (Windows) and `voiceover` (macOS) lanes run nightly or by hand.
- `release.yml` runs only by hand. `cut` bumps the next minor version and ships it end to end, and `cut-dry-run` rehearses that. `publish` publishes a version that's already committed, and `dry-run` rehearses that.

## Never weaken a check

When a check fails, sort the failure first: environment drift, your regression, an older failure, or a flaky test. Then fix the cause.

- Don't skip, delete or loosen a test to make it pass.
- Don't add retries to Vitest, Playwright or the workflow.
- Raise a timeout only with a measured reason.
- Move a perf guard's anchor only with `pnpm perf:guard:accept <guard> "<subject>" --reason "<one line>"`. It fails without `--reason`.
