## Where things live

- `website/pages/` holds the pages. A file's path is its URL: `pages/concepts/state.mdx` is `/concepts/state`.
- `website/nav.ts` is the one list of pages. The sidebar, the pager and the document head all read it. A new page needs an entry with a `title`, an `href`, an `icon` and a one-sentence `description`.
- `website/components/figures/<page>/` holds the drawings and live demos, one folder per figure.
- `website/components/docs/` holds the page parts: `Code`, `Callout`, `Collapsible`, `Subtitle`, `PageMeta` and the sidebar.
- `website/styles/global.css` holds the tokens, the type scale and the site-wide rules.
- `website/AGENTS.md` and `website/README.md` hold the styling and layout rules. Read them before you touch a component.

## The shape of a page

Each page is an `.mdx` file. After its imports, `<SiteNavbar />` and `<Sidebar />`, it opens with these, in order, and nothing else:

1. A `#` title that makes a claim or names a task: "Create an app", not "Overview".
2. `<PageMeta time assumes />`. `time` comes from the formula in `website/README.md`, so recompute it when you rewrite a page. `assumes` lists keys from the `concepts` map in `nav.ts`.
3. `<Subtitle text />`: one sentence that states the whole idea.
4. One small, real example: a code block or a figure.

Then come 3 to 6 `##` sections, each one idea, named as an instruction or a claim. Limits go last, as a "Not yet:" list. The page ends with one link to the next step.

Write for a reader who has never used a UI framework. Use short sentences, "you", and everyday examples like a guest list or an order ticket. Define each term where it first appears.

## Pick one visual per idea

| The idea | Use |
| --- | --- |
| "Try it and change it" | A `<Code>` block with `steps` |
| "Press this and watch which spots change" | A textbook column: a live demo with numbered notes beside it |
| The one thing the page must make the reader believe | An ink figure, drawn with the `markless-anatomy` skill |
| A command to run | `<Commands kind>` or `<CommandStrip command>` |
| Read-only code or config | A plain fenced block with a `title` |
| Facts to look up | A markdown table |
| A trap the reader will hit | One `<Callout>`, at most one per page |
| Background for someone who knows another tool | A closed `<Collapsible>` |

Most sections need no picture at all. Never put two visuals in a row: say what to do before one, and what to notice after it.

## Code the reader can edit

Wrap one or more titled fences in `<Code>`. The page needs no import, because the build adds it.

````txt
<Code steps={[{ label: 'Rename the button to `Done`.', shows: 'Done' }, { label: 'Start at `3` instead of `0`.', source: 'state(3)' }]}>
```tsrx title="tally.tsrx"
import { state } from '@markless/core';

export default function Tally() @{
	let fixed = state(0);

	<button onClick={() => fixed++}>Typos fixed: {fixed}</button>
}
```
</Code>
````

Each step ticks itself once the reader has done it:

| Field | The step ticks when |
| --- | --- |
| `shows` | an element in the result shows exactly this text |
| `source` | the code contains this text, spaces ignored |
| `rewrites` | one update rewrites at least this many places to the same text |

For a single suggestion, use `note="..."` instead of `steps`.

- Put `<Code>` and `</Code>` on their own lines, with only titled fences and blank lines between them.
- The first `.tsrx` fence is the entry: its default export is what the result shows. To pick another, write `<Code entry="page.tsrx">`.
- The starter must build. A broken starter stops the site build.
- Files import each other by relative path, and can import `@markless/core` and `@markless/ui`.
- Leave a demo's cosmetic `<style>` out of the shown code. Every line you do show must do what it says.

Not in a block: icon tags like `<lucide.plus />`, which need the `ui()` build plugin, and routes, API routes or anything else that needs a server.

## A textbook column

Use one when the reader must see which spots change and which don't. Press **Fixed one** a few times:

<TypoNotes />

Ring 1 changes on every press, and the tally counts the handler. Nothing else on the sheet moves. Here is the figure's markup, trimmed to one spot:

```tsrx
<MarginNotes said={said}>
	<InkScreen url="docs.app/typos" label="Live preview of the typo tally">
		<p><Ring n={1} /> Typos fixed: {fixed}</p>
		<InkButton onClick={() => fixed++}>Fixed one</InkButton>
	</InkScreen>
	<Notes>
		<NoteTitle>2 spots on this sheet</NoteTitle>
		<Spots>
			<Spot n={1} code={'{fixed}'}>the count, rewritten on each press</Spot>
		</Spots>
		<Tally>The handler ran <strong>{fixed}</strong> times.</Tally>
	</Notes>
</MarginNotes>
```

- `MarginNotes` and its parts come from `components/figures/ink/margin-notes.tsrx`, and `Ring` from `ring.tsrx` beside it.
- Each `Spot` number matches a `Ring` on the sheet.
- `said` is one plain sentence a screen reader hears after each change.
- Never put `Ring`, or any other imported component, inside an `@if` arm or an `@for` row. Draw the ring inline from `art.ring.ink` instead, as `figures/reading/blocks-demo.tsrx` does. A component there makes the browser render the arm, and pulls its code into every page's prefetch.

## Check the facts, then the page

Check every API name, import path, flag and command against the Markless source before you write it: package code, tests, fixtures and the CLI templates.

- Treat specs as pointers, not proof.
- If you can't check a fact, leave it out.
- Read versions and protocol facts from the package that owns them. Never type them by hand.
- Give byte figures a label: downloaded at load, downloaded on demand, or executed at load.

Then run the checks:

```bash
pnpm --dir website run typecheck   # the .tsrx-aware checker over pages and components
pnpm run typecheck                 # the rest of the repo
pnpm ci:local --fast               # CI's fast jobs
```

On a pull request that touches `website/`, CI runs two more jobs:

- `website-boxes` runs the site's tooling tests, then its browser checks against the dev server.
- `build-warnings` builds the whole site and fails on any warning the build prints.

Before you ask for review, open each page you changed in the light and dark theme, on a wide window and a phone-sized one.
