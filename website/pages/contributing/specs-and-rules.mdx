## Specs: the behavior contract

- `specs/framework-design.md` is the index. Read it first.
- `specs/framework/00-overview.md` to `14-emission-codegen-migration.md` each own one area, such as `03-state-graph.md` or `07-diagnostics.md`.
- `specs/framework/08-deferred-decisions.md` lists the topics that stay open on purpose.
- `specs/router/` covers routing, typed routing and the router CLI.
- `specs/framework/archive/` is history, not the current contract.

## Edit a spec

Follow `.ruler/skills/markless-spec-maintenance/spec.md`:

- Keep accepted decisions, unless your task reopens them.
- Record an open topic as deferred. Don't decide it in passing.
- Write behavior a test can check, not storage shapes or exact compiler output.
- Check TSRX syntax with the TSRX MCP server, and record what you checked. If it isn't there, use `tsrx.dev/specification` and record that instead.
- Run `git diff --check` before you finish.

## Rules: one source in `.ruler/`

`pnpm rules` runs `ruler apply`. It writes `AGENTS.md`, `CLAUDE.md`, the skill copies and the MCP configuration. Never edit those outputs by hand.

- `.ruler/AGENTS.md` holds the rules for every agent.
- `.ruler/claude.md` holds extra notes for Claude.
- `.ruler/ruler.toml` lists the outputs and the MCP servers.
- `.ruler/skills/*/` holds the skills, such as `markless-implementation`, `markless-spec-maintenance` and `markless-component-research`.

After you edit `.ruler/`, run `pnpm rules` and commit what it writes. The `agent-files` CI job fails if the outputs drift from `.ruler/`, and the pre-commit hook checks the same when you stage a `.ruler/` file.

## Rules to know

- Run `pnpm run typecheck` and `pnpm ci:local --fast` before you call a change done.
- Write the test first. Run the narrowest failing test, then make the smallest change.
- Never run components again in the browser over server HTML. No virtual DOM, and no second build stack besides Rolldown and Vite.
- Keep compiler, runtime, serializer and render code free of Node-only APIs.
- Import protocol and config facts from the package that owns them. Don't copy them as literals.
- A merge, or a push to `main` or any shared branch, needs the owner's go-ahead for that one change set.
- A pull request stays open until every review finding, CodeRabbit's too, has an answer.
- Comments are a last resort: one short line, only for a fact the code can't show. Never task numbers or process notes. Doc comments on public props and types stay.
