# The first click, in each environment

<PageMeta time="5 min" assumes="state, events" sprite="rays" />

<ThemeToggle />

The counter is on the screen. No click code has run yet. Somebody presses the button.

Who hears that press? The answer depends on two things: where the page came from, and how simple the
component is. There are three paths, and this page walks each one.

| | Browser, direct module | Browser, general path | Server-rendered page |
| --- | --- | --- | --- |
| Who builds the first DOM? | The compiled module, once | Markless, from the compiled output, once | The server |
| Who listens? | A listener on each element with an event | One listener per event name on the container | The inline resumer, one listener per event name |
| What starts on the first click? | That click's symbol | That click's symbols, the state graph and the full runtime | The resume module, then what it needs |
| Inline script in the HTML? | No | No | Yes, if the page can react |

In all three, a click on the counter runs the handler and updates the text that reads `count`. The
component itself does not run again.

<FirstClick />

## Path 1: the direct browser module

This is the path the counter takes when you call `render()` in a browser. For a simple component,
the compiler writes a [direct browser module](/how-it-works/compiler).

At mount, that module does three things:

1. It clones the button from a template and fills in `Count 0`.
2. It builds the component's own small state graph: a `Map` holding `state:count`.
3. It adds a click listener to the button itself.

That is the whole setup. The full runtime never starts.

On the first click, the listener asks for `symbol:0` by ID. The module imports it once, then keeps
it. The symbol runs `count++` against the small graph. Then the module reads each text slot again,
and writes the ones whose value changed.

## Path 2: the general browser path

A component that is not simple enough for a direct module still renders with the same `render()`
call. Props, child components, a scoped `<style>` or a `computed()` each send it down this path.

At mount, Markless builds the DOM from what the compiler wrote. It also builds the same state and
view records that a server writes. Those records stay in memory. Then it adds one capture-phase listener
per event name to the container. That is _event delegation_: one listener on an ancestor element
handles events from everything inside it.

On the first matching event, the listener walks up from the target to the container. It looks up
the element plus the event name in the view record. If a record matches, Markless builds the state
graph, starts the full runtime, and loads that record's symbols.

Markless's own test for this path mounts a hand-built counter, then clicks once. The setup ran once, no symbol
loaded at mount, and the click loaded exactly one symbol. The test also checks that there is no
inline script and no payload script.

This path also starts work before the press. A pointer that moves onto an element with a click
record fetches that click's symbols. Focus on an element with key, input or press handlers does the same.
These loads never run the handler.

## Path 3: a server-rendered page

Here the server ran the component body, and the browser never runs it. The records arrive as two
JSON scripts inside the container, next to the inline resumer. [The payload](/how-it-works/payload)
shows that HTML.

This is where Markless [resumes](/how-it-works): the HTML arrives already wired.

When the page loads, the inline resumer does three things:

1. It reads the `markless/view` script and walks the container's elements once, in document order.
2. It maps each [locator](/how-it-works/compiler) to an element, by the element's position in that walk.
3. It adds one capture-phase listener per event name to the container. It imports no app code.

When a record matches, the resumer imports the page's resume module and passes the event to it.
The bundler generates that module from your component file. It queues events, so they run in the
order they fired. Then it picks one of two ways in:

- If the compiler replaced every event and text-update record on the page with specialized code,
  the module runs that code. The full runtime never starts.
- Otherwise it loads the full runtime and builds the state graph from the `markless/state` script.

The resumer also wakes early. A pointer that crosses onto an element with a press record imports
the resume module before the press lands. Focus on an element with a key, input or press record does the same. A
second crossing does not import again.
