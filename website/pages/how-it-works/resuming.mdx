# The first click, on each path

<PageMeta time="4 min" assumes="state, events" />

<Subtitle text="A server-rendered page arrives mid-game, so the first press carries on from it instead of running your components again." />

<ResumeAnatomy />

Press the board. The server left the page mid-game and wrote down where everything stands, so the browser only makes the next move. On a real page, a press runs one handler, and only the text it changes is redrawn.

## Three ways in

| | Browser, direct module | Browser, general path | Server-rendered page |
| --- | --- | --- | --- |
| Who builds the elements? | The compiled module | Markless, from the compiled output | The server |
| Who listens? | Each element with an event | The container, one listener per event name | The inline resumer, on the container |
| What starts on the first click? | That click's symbol | Its symbols, the state graph and the full runtime | The resume module, then only what it needs |

## On a server-rendered page

- Each element with a handler carries an `m:on` attribute. The inline resumer reads it off the pressed element and imports no app code until then.
- The press loads the page's *resume module*. If the compiler replaced the page's event and text-update records with specialized code, as for the cart, the full runtime never starts.
- A press during loading is replayed in order. A pointer or focus landing on a handler imports the module early, once.

## In the browser alone

- The [direct module](/how-it-works/compiler) puts a listener on the button and keeps state in a `Map`. After the handler, it rewrites only the text that changed.
- The general path, for props, child components, a scoped `<style>` or a `computed()`, listens on the container and starts the full runtime on the first matching event.

[The state graph](/how-it-works/state-graph) shows how one write finds the text that reads it.
