# One write wakes only its readers

<PageMeta time="3 min" assumes="state, computed, events" />

<Subtitle text="The compiler writes down who reads what before the page exists, so a write changes only the text that reads it." />

<Code note="Press Add to cart and watch which lines change. Then add <p>{bags * 2} cups</p> and press again: the new line follows too.">
```tsrx title="cart.tsrx"
import { computed, state } from '@markless/core';

export default function Cart() @{
	let bags = state(2);
	const total = computed(() => bags * 14);

	<section>
		<p>House blend · 250 g</p>
		<p>In your cart: {bags} bags</p>
		<p>Total: ${total}</p>
		<button onClick={() => bags++}>
			Add to cart
		</button>
	</section>
}
```
</Code>

A press changes two lines:

- `In your cart` reads `state:bags` directly.
- `Total` reads `computed:total`, which reads `state:bags`.
- The product line reads nothing, so no press ever touches it.

Nothing runs the component again to find out which lines those are.

## Three parts make the state graph

The *state graph* is the list of who reads what, kept while the page runs:

- A **node** holds one value. `state()` makes one with an ID like `state:bags`, and `computed()` makes one like `computed:total`.
- A **subscription** is one reader: a node, a path into its value, and a small function to run when that path changes.
- The **journal** is the list of page changes those functions return, such as "set this text".

## One write, step by step

The full graph lives in `@markless/runtime`. For `bags++` it does this:

1. If the new value equals the old one, it stops.
2. Otherwise it stores the value and marks the written path as changed.
3. It marks `computed:total` as stale, because `total` depends on `bags`.
4. It schedules one flush as a *microtask*: a job that runs right after the current code finishes.
5. The flush runs each subscription whose path meets a changed path. Reading `total` recomputes it now.
6. Each subscription returns a journal entry, and Markless applies the entries to the page.

Two writes in the same turn share one flush. A handler that writes `3` and then `4` leaves one entry, showing `4`.

## Paths, not whole objects

A subscription listens to a path inside a value. Two paths meet when one starts with the other. With `let order = state({ bags: 2, grind: 'whole' })`, a write to `order.grind` doesn't wake the reader of `order.bags`. Replacing `order` wakes both, because the empty path starts every path.

A computed node lists the paths it reads. A write to one of them marks it stale, and it recomputes on its next read, not before.

## What the journal holds

| Entry | What it does |
| --- | --- |
| `setText` | Sets the text of one text node |
| `setAttr`, `setProp` | Sets one attribute, or one DOM property |
| `insertRange`, `removeRange`, `moveRange` | Inserts, removes or moves a run of nodes, such as an `@if` branch |
| `runCleanup` | Runs a cleanup registered for one element |

Nothing compares an old page with a new one, and `@markless/core` has no effect function: the compiler plans every subscription.

Where the graph is smaller or bends:

- A component on the [direct module](/how-it-works/compiler) skips this machinery. Its graph is a `Map`, and after a handler it reads each text slot again.
- An `@if` or `@switch` inside `@try` that holds a component re-renders the whole `@try` block when it toggles. The compiler warns with `MARKLESS_TRY_BLOCK_TOGGLE_RERENDER`; move the component outside the `@if`.

[Lazy chunks](/how-it-works/lazy-chunks) shows where the functions behind each subscription live.
